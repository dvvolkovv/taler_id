# Чат комнаты Taler ID — API для внешнего ассистента

Документ для интеграции стороннего ассистента (Linkeon) с чатом голосовой
встречи Taler ID. Все примеры сняты с живого сервера 2026-09-07, не по памяти.

## Где это работает сегодня

| Окружение | База | Отправка | Чтение |
|-----------|------|----------|--------|
| DEV | `https://staging.id.taler.tirol` | да, новая | **да** |
| TEST | `https://id.taler.tirol` | да, старая (отдаёт только `ts`) | нет, `404` |
| PROD | `https://api.talerid.io` | да, старая | нет, `404` |

Интеграцию сейчас можно вести **только против DEV**. На TEST и PROD ручка
чтения появится после раскатки; отправка там существует давно, но старая — без
номеров сообщений и без ленты, читать оттуда нечего.

## Доступ

Ассистенту не нужен аккаунт Taler ID. Достаточно кода комнаты — того же, что в
ссылке-приглашении `https://<база>/room/<код>`.

```bash
curl -X POST https://staging.id.taler.tirol/voice/rooms/public/<код>/join \
  -H 'Content-Type: application/json' \
  -d '{"name":"Linkeon"}'
```

```json
{
  "token": "eyJhbGciOiJIUzI1NiJ9.eyJ…",
  "roomName": "tmp-a1b8bcb6-bb4b-4d48-94d2-35c77e872dfc"
}
```

- `token` — доступ **только к этой комнате**, живёт 6 часов. Его же кладём в
  `Authorization: Bearer …` во все вызовы ниже.
- `roomName` — им адресуются обе ручки. Код комнаты и `roomName` — разные вещи.
- Если у комнаты пароль, он передаётся в том же теле: `{"name":…,"password":…}`.
- Подключаться к WebRTC не нужно: чат работает по HTTP, ассистент может не быть
  участником звонка в смысле медиа.

## Отправка

```bash
curl -X POST https://staging.id.taler.tirol/voice/rooms/<roomName>/chat \
  -H "Authorization: Bearer $TOKEN" -H 'Content-Type: application/json' \
  -d '{"text":"Смотри материалы: https://example.com/doc","name":"Linkeon","clientMsgId":"lnk-0001"}'
```

```json
{ "ts": 1788798156037, "seq": 1, "msgId": "c_19346087_lnk-0001" }
```

| Поле | Обязательно | Смысл |
|------|-------------|-------|
| `text` | да | до 500 символов, пробелы по краям срезаются |
| `name` | нет | подпись отправителя, до 64 символов; по умолчанию `Taler ID` |
| `clientMsgId` | нет | свой идентификатор, `[A-Za-z0-9_-]`, 1–64 символа |

`clientMsgId` нужен, если ассистент **одновременно читает ленту**: по нему он
узнаёт собственные сообщения, не дожидаясь ответа на запрос. Сервер строит из
него итоговый `msgId` вида `c_<хеш отправителя>_<clientMsgId>` — поэтому один и
тот же `clientMsgId` у разных отправителей не сталкивается. Негодное значение
молча заменяется серверным идентификатором, отказа не будет.

Это же значение возвращается в ленте (см. ниже) и в пакете, который получают
участники встречи. То есть своё сообщение опознаётся тремя независимыми путями —
по ответу на запрос, по ленте и по эху, — и ни один из них не обязателен:
потерянный ответ или обогнавшая его лента не оставят ассистента в неведении.

## Чтение

```bash
curl "https://staging.id.taler.tirol/voice/rooms/<roomName>/chat?since=<seq>" \
  -H "Authorization: Bearer $TOKEN"
```

```json
{
  "messages": [
    { "msgId": "c_19346087_lnk-0001", "text": "Смотри материалы: https://example.com/doc",
      "name": "Linkeon", "ts": 1788798156037, "seq": 1, "own": true },
    { "msgId": "server_8b983c0d-4048-4b50-810c-dd0ca3eeab6f", "text": "ответ человека",
      "name": "Taler ID", "ts": 1788798156075, "seq": 2, "own": false }
  ],
  "seq": 2,
  "truncated": false
}
```

- `since` необязателен: без него вернётся вся лента встречи. С ним — только
  сообщения новее указанного номера.
- `clientMsgId` присутствует у сообщений, отправленных с этим полем. У
  остальных ключа **нет вовсе** — проверять наличием ключа, а не сравнением с
  пустым значением.
- `seq` в корне ответа — курсор для следующего запроса. Хранить и передавать
  нужно именно его, а не время: метки времени у двух сообщений совпадают чаще,
  чем кажется.
- `own` — сообщение отправлено **этим же токеном**. Идентификаторы участников
  наружу не отдаются, только этот признак.
  ⚠️ Признак живёт ровно столько, сколько токен. Гостевой вход выдаёт новую
  личность при каждом обращении к `/join`, поэтому после переподключения ваши
  прежние сообщения вернутся с `own: false` — это не сбой, а устройство модели:
  сервер не знает, что новый гость и прежний — один и тот же ассистент. Если
  опознание своих сообщений нужно и после переподключения, храните `msgId` из
  ответов на `POST` и сверяйте с лентой — они не меняются. У залогиненных
  участников Taler ID личность привязана к сессии, и там `own` переподключение
  переживает.
- `truncated: true` — между вашим курсором и первым отданным сообщением
  **возможно** есть пропуск: лента переполнилась (потолок 500 сообщений),
  началась новая встреча, или курсор указывает в будущее. Это подсказка
  «перечитайте ленту целиком», а не гарантия потери.

Опрос: чат — не поток событий, разумный интервал 2–5 секунд. Держать
`GET` в цикле без паузы не нужно и упрётесь в ограничения ниже.

## Жизненный цикл ленты

Чат живёт **ровно одну встречу**.

- Когда в комнате начинается новая встреча (входит первый участник, а прежних
  не осталось), лента предыдущей стирается.
- Нумерация при этом **не** обнуляется: номера продолжают расти. Поэтому
  застрявший курсор прошлой встречи получит `truncated: true` и новые
  сообщения, а не тишину.
- Если следующей встречи не случится, лента исчезнет сама через сутки.
- Ничего не сохраняется в базу: после встречи переписки не остаётся.

## Ошибки

| Код | Когда | Что делать |
|-----|-------|-----------|
| `400` | пустой текст или длиннее 500 символов | поправить сообщение |
| `401` | нет заголовка `Authorization` | получить токен |
| `403` | токен выдан на другую комнату | получить токен на нужную |
| `429` | превышен потолок | подождать и повторить |
| `503` | недоступно хранилище ленты | повторить позже, это временно |

Потолков два, и они различаются текстом ответа:

- `"too many chat messages, slow down"` — **чат**: 10 сообщений за 10 секунд с
  одного отправителя в одну комнату;
- `"ThrottlerException: Too Many Requests"` — **общий на сервис**: 10 запросов
  в секунду, 100 в минуту, 1000 в час.

## Чего пока нет

- **Картинки.** Поле для вложения и ручка загрузки спроектированы, но не
  сделаны. Сейчас можно прислать только текст; ссылка на картинку приедет
  ссылкой.
- **Кликабельные ссылки.** Ссылка доходит и видна, но в клиентах пока
  отображается обычным текстом — нажать нельзя, надо копировать. Правится
  отдельной задачей.
- **Сообщения людей из старых клиентов не попадают в ленту.** Мобильное
  приложение (и веб-комната до ближайшей раскатки) публикуют чат напрямую в
  data-канал LiveKit, мимо сервера. Такие сообщения ассистент через `GET` не
  увидит: он прочитает только то, что отправлено через API. Это переходное
  состояние — оно закончится, когда доедут клиентские правки.

## Рекомендуемый порядок работы

1. Получить токен по коду комнаты, запомнить `roomName`.
2. Прочитать ленту без `since` — это состояние встречи на момент подключения.
3. Дальше опрашивать с `since=<последний seq>` раз в 2–5 секунд.
4. При `truncated: true` перечитать ленту целиком без `since`.
5. Отправлять с `clientMsgId`, чтобы отличать свои сообщения от чужих в ленте
   (или пользоваться `own`).
6. На `429` — пауза, на `503` — повтор позже; оба временные.
