# Recorder: защита длинных записей от обрыва при конвертации

**Date:** 2026-11-05  
**Status:** спецификация одобрена пользователем; план реализации подготовлен
**Scope:** LiveKit recorder, сохранение статуса при транскрибации, отображение частичной записи в мобильном приложении

## Цель

Не допускать обрыва PCM→OGG/MP3 конвертации по произвольному общему таймауту. При реальном сбое сохранять всё доступное аудио со статусом `partial`, не выдавая частичный результат за полный.

## Контекст и доказанная причина

Встреча PROD `4870181f-6efd-488e-9a01-4b79f414231b` от 2026-11-04 длилась 6 783 секунды. Три PCM-дорожки по ~621 МБ завершались ровно через 270 секунд, поскольку `calcFfmpegTimeout` выделял `60s + ceil(MB/100) × 30s`. Реальная конвертация занимала больше времени. В финальный MP3 попали только две короткие дорожки с последними ~22 минутами, а запись получила `status=done`. Whisper на цифровой тишине выдал повторяющееся `you`.

Исходные PCM сохранились, встреча восстановлена вручную 2026-11-05. Этот документ описывает постоянное исправление, а не восстановление конкретной встречи.

Текущий `livekit-agent/recorder.js` одинаков на `origin/main`, `origin/dev` и PROD. Существующий `recorder-endpoints.test.js` проверяет только URL backend-вызовов; таймауты и обработка частичных ошибок тестами не покрыты.

## Требования

- Рабочая конвертация не имеет общего ограничения по длительности.
- Действительно зависший ffmpeg не может оставаться вечно в `processing`.
- Все живые этапы конвертации используют один механизм контроля: PCM→OGG участника, объединение нескольких дорожек участника, финальный MP3.
- Ошибка одной дорожки не удаляет успешно записанные остальные.
- Любая потерянная дорожка переводит собранное аудио в `partial`; `done` означает отсутствие ошибок обработки.
- Если из-за ошибок не создан доступный пользователю файл записи, результат — `failed`, а не `partial` или `done`.
- Повторная транскрибация не меняет `partial` обратно на `done`.
- PCM при ошибках сохраняется для ручного восстановления, как сейчас.
- Пользователь видит предупреждение о частичной записи в мобильном приложении.
- Изменение не требует миграции БД: `MeetingSummary.status` уже строка.

Вне scope: потоковая конвертация во время записи, изменение Whisper-чанкинга, переработка биллинга, автоматическая повторная обработка всех старых частичных встреч.

## Рассмотренные подходы

| Подход | Плюсы | Минусы | Решение |
|--------|-------|--------|---------|
| **Watchdog по прогрессу ffmpeg** | Нет предела длительности; зависание ограничено; подходит любым записям | Нужен отдельный процесс-раннер и тесты | **Выбран** |
| Увеличенный таймаут от размера/длительности | Минимальный diff | Сохраняется произвольный предел, зависящий от скорости хоста | Отклонён |
| Потоковая конвертация во время записи | Меньше постобработки | Большая архитектурная переделка и новый класс рисков | Не входит в этот релиз |

## Архитектура

```text
PCM участника ─┐
PCM участника ─┼─> runFfmpegProcess ─> OGG ─┐
PCM участника ─┘       │                    ├─> runFfmpegProcess ─> MP3 ─> S3
                       │                    │
                       ├─ прогресс time=... продолжается → ждать без общего лимита
                       └─ нет прогресса 5 минут → SIGTERM → SIGKILL → ошибка дорожки
```

Новый небольшой Node-модуль `livekit-agent/ffmpeg-process.js` запускает ffmpeg через `child_process.spawn` и предоставляет `runFfmpegProcess(args, options)`.

### Контроль прогресса и завершения

- Раннер читает `stderr` и распознаёт монотонно возрастающие значения `time=HH:MM:SS.xx`.
- Общего deadline нет. Пока значение времени продвигается, процесс продолжается независимо от длительности записи.
- Отсутствие нового прогресса в течение 300 секунд считается зависанием. Порог передаётся опцией для коротких unit-тестов.
- При зависании раннер отправляет SIGTERM; если процесс не завершился за 10 секунд — SIGKILL. Promise отклоняется с машинно различимым кодом `FFMPEG_STALLED` и хвостом stderr для диагностики.
- Ненулевой exit code и ошибка запуска процесса также отклоняют Promise с хвостом stderr. Таймеры и listeners очищаются при любом исходе.
- stdout/stderr в памяти ограничиваются хвостом, чтобы прогресс-лог многочасовой конвертации не раздувал процесс Node.

`recorder.js` использует раннер во всех перечисленных живых вызовах. `calcFfmpegTimeout` и `calcMixTimeout` удаляются вместе с логами «timeout N s»; новые логи фиксируют запуск, завершение и stall. Неиспользуемые в рабочем пути вспомогательные функции не расширяются и не рефакторятся.

## Статус результата и ошибки

| Ситуация | Аудио | Статус | PCM |
|----------|-------|--------|-----|
| Все дорожки и финальный mix успешны | Полное | `done` | Удаляется по текущему правилу |
| Одна или несколько дорожек не конвертированы, остальные собраны | Частичное | `partial` | Сохраняется |
| Все дорожки потеряны / нет аудио | Нет | Существующий `failed_no_audio` или `failed` по текущему пути | Сохраняется при ошибке обработки |
| Финальный mix и оба пути сохранения (S3 и локальный fallback) завершились ошибкой | Нет доступного файла | `failed` | Сохраняется |
| ffmpeg не продвигается 5 минут | Остальные дорожки продолжают обработку | `partial`, если есть собранное аудио; иначе `failed` | Сохраняется |

Статус вычисляется от фактического результата: при наличии `recordingUrl` — `hadErrors ? 'partial' : 'done'`, без него — `failed`. Catch финального mix/upload также устанавливает `hadErrors`, чтобы PCM не удалялись после неуспешной финальной стадии. Успешный локальный fallback после ошибки S3 считается доступной записью и не делает её частичной сам по себе.

В `VoiceService.runTranscription` финальное обновление сохраняет `partial`, если встреча пришла с этим статусом; для остальных успешных расшифровок остаётся `done`. Возвращаемый методом статус должен совпадать со статусом в БД. Состояние `processing` и поведение возвратов при ошибках Whisper не меняются.

## Мобильное приложение и ассистент

- `MeetingCardState` получает значение `partial`; `partial` не относится ни к `processing`, ни к `failed`.
- Карточка встречи показывает жёлтую метку «Запись частичная» / «Partial recording» и остаётся открываемой.
- Экран встречи показывает предупреждение, что часть дорожек не обработана и доступные запись/транскрипт могут быть неполными.
- Карточка аудиозаписи получает то же краткое предупреждение без блокировки воспроизведения, скачивания и повторной транскрибации.
- `get_meeting_summary` добавляет `partialRecording: true` для статуса `partial`, чтобы ассистент не называл такой протокол полным.
- Новые строки добавляются одновременно в `app_ru.arb` и `app_en.arb`; шаблон локализации остаётся английским.
- Старые мобильные версии классифицируют неизвестный статус как обычную встречу. Это совместимо с серверным исправлением обрыва, но предупреждение появится только после мобильного релиза.

## Тестирование и критерии приёмки

1. **TDD, unit:** сначала красные тесты раннера, затем реализация. Проверить:
   - процесс, живущий дольше прежнего 270-секундного лимита по модели времени теста и регулярно сообщающий прогресс, завершается успешно;
   - отсутствие прогресса приводит к `FFMPEG_STALLED`, SIGTERM и резервному SIGKILL;
   - ненулевой exit и ошибка spawn возвращают диагностику;
   - таймеры/listeners не оставляют висящих handles.
2. **Статусы:** тест recorder фиксирует `partial` при потере части дорожек и `failed` без доступного результата, включая ошибку финального mix/upload; backend-тест доказывает, что успешная транскрибация сохраняет `partial`; Flutter-тест классифицирует `partial` отдельно от `ready` и `failed`.
3. **Реальная длинная дорожка на DEV:** синтетическая PCM продолжительностью около двух часов и размером не менее 621 МБ проходит конвертацию дольше прежнего лимита без обрыва; выходной OGG имеет ожидаемую длительность. Пользовательские PCM для теста не используются.
4. **Существующие наборы:** `node --test` в `livekit-agent`, backend tests, `flutter test`.
5. **E2E на DEV:** `test:recording`, `test:speakers`, `test:voice-session`; после изменения транскрибации — обязательный `verify-long-transcription.ts`.
6. **Мобильный релиз:** обязательный emulator UI integration test и все обязательные проверки релиза из CLAUDE.md.

Критерий успеха: длинная встреча сохраняет все полученные дорожки без общего timeout; при принудительном сбое одной дорожки пользователь получает остальные со статусом `partial`, предупреждением и сохранёнными PCM.

## Выкачка и совместимость

- Сначала отдельная выкатка recorder/backend на DEV и обязательные smoke/e2e проверки.
- TEST — отдельная команда после успешного DEV.
- PROD — только по отдельному явному указанию пользователя, после TEST и согласованного мобильного релиза.
- Миграции БД нет. Изменения статуса обратно совместимы на уровне схемы.
- Восстановленную встречу `4870181f…` повторно не изменяем; её резервные копии не удаляем в рамках этого исправления.
