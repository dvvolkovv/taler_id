# Партнёрский API мессенджера (первый партнёр — nadi) — Design

**Date:** 2026-09-30
**Status:** Approved (design), pending implementation plan
**Scope:** сторона TalerID — партнёрский API, доступ к мессенджеру по партнёрскому токену, вебхуки, документация для интеграторов и тестовый клиент. Бэкенд (`selyanska`, nadi.me) и приложение (`nadi-app`) nadi дорабатывает команда nadi по документации из этого спека.

## Цель

nadi — Flutter-приложение громад с Next.js-бэкендом на nadi.me. Нужно, чтобы его пользователи **автоматически** получали аккаунт TalerID и переписывались друг с другом **в интерфейсе nadi**: личные чаты, группы, файлы, realtime. Движок переписки — существующий мессенджер TalerID.

## Контекст

**nadi сегодня:** собственная переписка — только личные «листи» 1:1, экран опрашивает сервер раз в 4 секунды; пользователи не могут сами создавать группы; писать можно только «связанным» (друзья или уже переписывались). Пуши не подключены (ключей нет, 0 устройств). 163 пользователя, 150 сообщений, за последние 30 дней — ни одного. Каждый пользователь nadi входит по почте с кодом, почта уникальна.

**TalerID сегодня:**
- Мессенджер полный (группы с ролями, файлы, ответы, закрепы, Socket.IO с Redis-адаптером на две ноды PROD), но REST `/messenger/*` и сокет принимают **только собственный токен входа TalerID** (`JwtAuthGuard`, `isApiAccessToken`).
- Отправка, правка, удаление, реакции и отметки о прочтении — только через сокет.
- Личный чат требует принятого контакта (`ContactRequest` ACCEPTED); группы — нет.
- Пуши уходят только в приложение TalerID (один Firebase-проект). Исходящих вебхуков нет.
- Есть `POST /partner/provision` (`src/partner/`) — сделан под Linkeon: заводит пользователя по телефону и выдаёт OIDC-токены только для `/mcp`. Модуль жёстко привязан к Linkeon (константы клиентов, `LINKEON_PARTNER_SECRET`).

## Ключевые решения

| Вопрос | Решение |
|--------|---------|
| Кто что делает | TalerID — этот спек. nadi — своя сторона по документации |
| Кем становятся люди nadi | **Полноценными аккаунтами TalerID**, один на почту. Позже могут войти в приложение TalerID и видеть те же чаты |
| Почта уже занята аккаунтом TalerID | **Привязка только по коду из письма**, который TalerID шлёт на эту почту. Без кода nadi не получает доступ к существующему аккаунту |
| Кто кому пишет в личку | **Друзья nadi = контакты TalerID.** Бэкенд nadi синхронизирует дружбу вызовами API; правило «личка — только контактам» проверяет сервер TalerID |
| Как приложение nadi работает с мессенджером | **Напрямую:** бэкенд nadi выдаёт приложению токен мессенджера на 15 минут, приложение ходит в REST и сокет TalerID само |
| Вид токена | **Опаковый OAuth-токен со scope `messenger`**, а не токен входа TalerID. По умолчанию не принимается нигде, кроме явно помеченных ручек мессенджера |
| Уведомления, когда чат не открыт | **Подписанный вебхук** `message.created` на бэкенд nadi; пуш шлёт nadi своими ключами и со своими тихими часами |
| Linkeon-модуль | Не трогаем. Новый модуль рядом, перенос Linkeon — отдельной задачей |

## Архитектура

```
nadi-app (Flutter)                       бэкенд nadi (nadi.me)
   │  токен на 15 мин  ◀──────────────────  │  Authorization: Bearer tidp_nadi_…
   │                                        │
   │ REST /messenger/*  +  Socket.IO /messenger          │ /partner/v1/*
   ▼                                        ▼
TalerID (NestJS, DEV / TEST / PROD)
   src/partner-api/         ← новый модуль: связки, токены, контакты, вебхуки
   src/messenger/           ← MessengerAuthGuard, @PartnerAllowed, правила
   src/oidc/                ← scope `messenger`
        │
        └── BullMQ `partner-webhooks` ──▶ POST на адрес вебхука nadi (путь выбирает nadi), подпись HMAC
```

Компоненты `src/partner-api/`:
- `partner-key.guard.ts` — ключ партнёра, белый список IP, выключатели; кладёт `req.partner`.
- `partner-users.service.ts` — связки: создание аккаунта, привязка по коду, отзыв, удаление управляемого аккаунта.
- `partner-tokens.service.ts` — один грант OIDC на связку, выпуск токенов по нему.
- `partner-contacts.service.ts` — контакты по дружбе nadi.
- `partner-webhooks.service.ts` + процессор BullMQ — постановка, подпись, доставка, журнал.
- `scripts/partner-admin.ts` — завести партнёра, выпустить или сменить ключ, задать вебхук.

## Термины

- **Связка** (`PartnerLink`) — «партнёр + `externalId` ↔ пользователь TalerID». Статусы: `PENDING` (ждёт кода), `ACTIVE`, `REVOKED`.
- **`externalId`** — стабильный id человека у партнёра (для nadi — id участника). 1–128 символов `[A-Za-z0-9._:-]`.
- **Управляемый аккаунт** — аккаунт, созданный этим партнёром, в котором человек ни разу не задавал пароль TalerID. Только такой аккаунт партнёр может переименовать, удалить, и только такой скрыт из глобального поиска. Как только человек задал пароль (например, через «забыли пароль», чтобы войти в приложение TalerID), аккаунт перестаёт быть управляемым. Кто завёл аккаунт, помнит сам аккаунт (`User.createdByPartnerId`), а не связка: строку связки переиспользуют под другой аккаунт.

## Партнёрский API

База `/partner/v1`. Все запросы — `Authorization: Bearer tidp_<slug>_<секрет>`; slug партнёра — `[a-z0-9-]`, секрет — 256 случайных бит в base64url. Ошибки — стандартный формат TalerID: машинный код в `message`, дополнительные поля рядом (`attemptsLeft`, `retryAfter`).

Отказы доступа: выключатель `PARTNER_API_ENABLED` не `true` или партнёр выключен → `403`; неверный ключ или IP не из белого списка → `401`.

### `POST /partner/v1/users`

Тело: `{ externalId, email, firstName?, lastName?, locale? }`. Почта приводится к нижнему регистру, поиск существующего аккаунта — точное совпадение без учёта регистра, `lower(email) = lower($1)` (уникальный индекс в БД регистрозависим, иначе `Ivan@…` и `ivan@…` стали бы двумя аккаунтами). Не фильтр Prisma `mode: 'insensitive'`: на PostgreSQL он становится `ILIKE`, и `_`/`%` в адресе работали бы как шаблон. `locale`: `ru`/`en` сохраняются в профиль, остальное → `en`.

Аккаунт и связка пишутся одной транзакцией, переиспользуемая строка связки — только если она всё ещё та полностью отозванная, что прочитана. Параллельные запросы про одного человека повторяются с начала до трёх раз, дальше `503 link_busy`.

| Ситуация | Ответ |
|---|---|
| Связка с этим `externalId` уже `ACTIVE` | `200 {status:'active', talerUserId, created:false}`. Почта из запроса игнорируется: после первой привязки связку определяет `externalId` |
| Связка `PENDING` | `200 {status:'confirmation_required', talerUserId:null}` |
| Почта свободна | Создаётся аккаунт → `200 {status:'active', talerUserId, created:true}` |
| Почта принадлежит аккаунту, не привязанному к партнёру | Связка `PENDING`, **письмо не отправляется** → `200 {status:'confirmation_required', talerUserId:null}`. Id чужого аккаунта не раскрывается |
| Этот аккаунт уже привязан к партнёру под другим `externalId` | `409 user_linked_to_other_external_id` |
| Связка была `REVOKED` | Те же правила, что при первой привязке: управляемый аккаунт — снова `active`, чужой — снова через код, удалённый — создаётся новый |
| Почту держит аккаунт, заблокированный администратором | `409 email_unavailable` |
| Параллельные запросы не разошлись за три попытки | `503 link_busy` — повторить |

Новый аккаунт получает тот же набор записей, что при обычной регистрации: `User` (почта, `emailVerified=true` — nadi проверил её своим кодом, это обязанность партнёра), `Profile` (имя, язык), `KycRecord`, подписку на системный канал новостей. Пароля нет. Письмо при массовой первичной загрузке не отправляется — только по явному `link-code`.

> Подписка на канал новостей — как у всех: `SystemChannelService.ensureSeeded()` при каждом старте бэкенда подписывает всех неудалённых пользователей, так что исключение при создании всё равно откатилось бы после рестарта. Для nadi каналы скрыты на уровне API (см. ниже).

### `POST /partner/v1/users/{externalId}/link-code`

Только для связки `PENDING`. Шлёт 6-значный код на почту существующего аккаунта. Код живёт 10 минут, хранится как HMAC; повторная отправка не чаще раза в 60 с и не больше 5 в час на связку. Письмо — на языке профиля TalerID: «Приложение Nadi просит доступ к вашим чатам Taler ID. Код: … Если это не вы — проигнорируйте письмо: без кода доступ не откроется».

Лимиты на связку считаются по человеку (партнёр + аккаунт), а не по строке связки: перепривязка под другим `externalId` их не обнуляет. Кроме них — общий суточный потолок партнёра: 1000 выданных кодов и 3000 сравнений кода; отклонённые запросы и проверки без сравнения его не расходуют, иначе цикл повторов у клиента выключил бы привязку всему партнёру на сутки. Первое превышение пишется в лог как ошибка — это атака или сломанный клиент. На одну жертву перебор безнадёжен (5 попыток на код, 5 писем в час, каждое письмо видит сам человек), но без общего потолка утёкший ключ перебирал бы тысячи чужих аккаунтов параллельно. Лимиты отправки и проверки без Redis отказывают (`503 rate_limiter_unavailable`), а не пропускают.

Ответы: `200 {sent:true, expiresIn:600}`; `404 not_linked`; `409 not_pending`; `429 too_many_requests {retryAfter}`; `503 email_send_failed`; `503 rate_limiter_unavailable`.

### `POST /partner/v1/users/{externalId}/link-code/verify`

Тело `{code}`. Ответы: `200 {status:'active', talerUserId}`; `400 invalid_code {attemptsLeft}`; `410 code_expired` — истёк или сожжён после 5 ошибок, нужен новый `link-code`; `429 too_many_requests {retryAfter}` — суточный потолок проверок партнёра; `503 rate_limiter_unavailable` — потолок не проверить (Redis). Попытка списывается в БД до сравнения; неверные и сжёгшие код попытки пишутся в `AuditLog` (`PARTNER_LINK_CODE_FAILED`), чтобы перебор был виден не только по письмам.

### `POST /partner/v1/users/{externalId}/token`

`200 {accessToken, tokenType:'Bearer', expiresIn:900, talerUserId}`. Ошибки: `404 not_linked` (в том числе если связку отозвали прямо во время запроса, и для `PENDING`-связки удалённого аккаунта — о судьбе аккаунта, к которому доступа не давали, партнёр не узнаёт), `409 confirmation_required`, `410 account_deleted` (аккаунт удалён или заблокирован в TalerID; связка отзывается сама). `410` получает только партнёр, который был допущен к аккаунту (связка подтверждалась) и не отвязал его сам ещё до удаления; остальным — `404`. Удаление аккаунта человеком отзывает связки сразу (`ProfileService.deleteAccount`), и `410` при этом сохраняется — по нему партнёр понимает, что заводить человека заново сам не должен, `503 link_busy` (редкая гонка параллельных запросов токена — повторить).

Любая ручка, которой приходится отзывать связку, при сбое Redis отвечает `503 revocation_unavailable` — повторить.

### `GET /partner/v1/users/{externalId}`

`200 {status:'active'|'confirmation_required'|'revoked', talerUserId|null, managed:boolean, linkedAt|null}`; `404 not_linked`. Связка удалённого аккаунта — `revoked`, если партнёр был к нему допущен (те же правила, что у `410` в `/token`), иначе `404`.

### `PATCH /partner/v1/users/{externalId}`

Тело `{firstName?, lastName?}`, `null` стирает поле. Только для управляемого аккаунта, иначе `409 profile_not_managed`; связки не `ACTIVE` — `404 not_linked`.

### `DELETE /partner/v1/users/{externalId}[?deleteAccount=true]`

Отзывает связку: статус `REVOKED`, `revokeByGrantId` гасит все её токены мгновенно, открытые сокеты связки рвутся (комната `plink:<linkId>`, через Redis-адаптер — на всех нодах). Аккаунт TalerID остаётся за человеком. `204`.

`deleteAccount` принимает только `true` или `false`, остальное — `400 invalid_delete_account` (тихое «не удалять» на `?deleteAccount=1` было бы отказом в стирании данных под видом успеха). С `deleteAccount=true` — ещё и удаляет аккаунт штатной процедурой `ProfileService.deleteAccount` (обнуляет почту, телефон, пароль; ставит `deletedAt`). Только для управляемого аккаунта, иначе `409 account_not_managed` и ничего не меняется. Повтор безопасен: уже удалённый аккаунт второй раз не удаляется, ответ тот же `204`. Нужно, когда человек удаляется из nadi и просит стереть данные; заодно так убирают за собой тесты.

### `PUT /partner/v1/contacts/{a}/{b}` и `DELETE …/{a}/{b}`

`a`, `b` — `externalId`, порядок не важен. Обе связки должны быть `ACTIVE`, иначе `409 link_not_active`; `a == b` → `400`.

- `PUT` — делает двоих контактами (строка `ContactRequest` ACCEPTED) и записывает `PartnerContact`. Если кто-то из них заблокировал другого — `409 blocked`, блокировку партнёр не снимает. `200 {contact:true, created:boolean}`.
- `DELETE` — удаляет `PartnerContact`; сам контакт TalerID снимается, только если его создал партнёр и его не держит другой партнёр. Если двое были контактами в TalerID до nadi, контакт остаётся. `200 {contact:boolean}` — остались ли контактами. Как и `PUT`, только для двух `ACTIVE`-связок: иначе ответ раскрывал бы, дружат ли два аккаунта, чьего согласия партнёр не получал.
- Признак «контакт завёл партнёр» сверяется на каждом `PUT` (завёл сейчас — `true`; контакт уже был — прежнее значение). Известная неточность: если люди сами удалят такой контакт в TalerID и сами же заведут заново, признак останется `true`, и `DELETE` партнёра снимет их собственный контакт. Точное отслеживание потребовало бы хранить id строк `ContactRequest`; принято как редкий случай.

### Вебхуки: `POST /partner/v1/webhooks/test`, `GET /partner/v1/webhooks/deliveries?limit=`

См. раздел «Вебхуки».

### Лимиты

Считаются **по партнёру, а не по IP**: `/token` — 600 в минуту, остальные ручки — 120 в минуту. Глобальные лимиты по IP (`short`/`medium`/`long`, среди них 1000 в час на эндпоинт) для этих ручек отключены — иначе выдача токенов с одного сервера nadi упрётся в них при первых же сотнях активных пользователей.

## Мессенджер с партнёрским токеном

### Проверка токена

`MessengerAuthGuard` заменяет `JwtAuthGuard` на контроллере мессенджера:
1. `@Public()` — пропустить.
2. Токен проверяется как собственный токен входа TalerID (подпись + `isApiAccessToken`) → `req.user = payload`, как сегодня. Для приложения TalerID ничего не меняется.
3. Иначе — поиск OIDC-токена (`provider.AccessToken.find`): не истёк, scope содержит `messenger`, клиент принадлежит включённому партнёру (кэш на 30 с) → `req.user = { sub: accountId, partner: { partnerId, linkId } }`. Остальной код мессенджера читает только `user.sub` и не меняется.
4. Партнёрский токен пускают только обработчики с `@PartnerAllowed()`; остальные отвечают `403 not_available_for_partner`. Новые ручки мессенджера по умолчанию закрыты для партнёров.
5. Иначе `401`.

Отдельная проверка статуса связки на каждый запрос не нужна: отзыв связки отзывает её грант, и токен перестаёт находиться.

Сокет (`handleConnection`) проверяет токен по той же схеме. Для партнёрского сокета: `client.data.partner = {partnerId, linkId}`, вход в комнаты `user:<id>` и `plink:<linkId>`, **отключение в момент истечения токена** — клиент переподключается со свежим. Для обычных сокетов поведение не меняется.

Остальные места, где принимается токен (`/profile`, `/tenant`, админка, голосовой прокси в `main.ts`, `room-access.guard`), партнёрский токен не пускают без каких-либо изменений: он опаковый и не проходит `jwt.verify`.

### Что открыто партнёру

- Личные чаты и группы: создание, участники и роли, переименование, выход, удаление, «без звука».
- История, синхронизация, отметки о прочтении, кто прочитал, поиск по своим сообщениям.
- Файлы: `POST /files`, загрузка по частям, `GET /files/url`. Скачивание (`/files/download`) и так публичное.
- Ответы, треды, пересылка, закрепы, превью ссылок.
- Список контактов (чтение), блокировка и разблокировка.
- Сокет: `join`, `message`, `edit_message`, `delete_message`, `typing`, `react_message`, `mark_read`, `thread_reply`.

### Что закрыто

- **Запросы в контакты** (отправка, принятие, отклонение): контакты заводит только синхронизация дружбы nadi. Иначе правило «личка — только друзьям» обходилось бы одним запросом.
- **Глобальный поиск людей** (`/users/search`) — он отдаёт почту.
- **Звонки TalerID** — все события `call_*` в сокете отвечают ошибкой. У nadi свои звонки.
- Каналы, ссылки-приглашения, публичные имена бесед, опросы, темы, отложенные сообщения, черновики/архив/закреп чата в списке, «Избранное», AI-аналитик, расшифровка голосовых.

### Только личные чаты и группы

Для партнёрского токена списки бесед (`/conversations`, `/sync`, `/read-state`) содержат только `DIRECT` и `GROUP`: канал новостей TalerID, «Избранное» и чаты AI-ассистентов в интерфейс nadi не попадают. Обращение к беседе другого типа по id — `403`, и через REST, и через сокет. Проверку лучше встроить в общую проверку участия в беседе, чтобы не размазывать её по обработчикам; как именно — решает план.

### Изменения правил

1. **Группы.** Партнёрский пользователь может добавить в группу (при создании и позже) только свои контакты, иначе `403 not_a_contact` со списком id. Для приложения TalerID поведение не меняется.
2. **Исправление: самопринятие запроса.** `acceptContactRequest` сейчас позволяет отправителю принять собственный запрос. Принять сможет только получатель. Касается всех пользователей.
3. **Исправление: контакт из разблокировки.** Блокировка удаляет контакт, а разблокировка создаёт его, даже если до блокировки контакта не было. `BlockedUser.hadContact` запоминает, был ли контакт, и разблокировка восстанавливает только его. Касается всех пользователей.
4. **Скрытие из поиска.** Управляемые аккаунты не попадают в `/users/search` ни для кого: человек не регистрировался в TalerID и не соглашался показывать почту незнакомым. Задал пароль — стал виден.
5. **Удаление аккаунта в TalerID** (самим человеком) отзывает все его партнёрские связки и гранты.

### CORS

Если чаты будут и в веб-кабинете nadi, в `ALLOWED_ORIGINS` каждого окружения добавляется `https://nadi.me`. Сокет уже принимает любой origin. Кода это не требует.

## Вебхуки

### Когда

В `MessengerGateway.fanOutToParticipants` — там же и при тех же условиях, что пуш в приложение TalerID: у получателя не открыт этот чат, чат не на «без звука» (упоминание пробивает), сообщение не «тихое». Дополнительно: только беседы `DIRECT` и `GROUP`, только получатели с действующей связкой у партнёра с настроенным вебхуком, не отправителю.

Все связки участников беседы загружаются **одним запросом до цикла**, а не на каждого участника: пошаговые запросы уже роняли рассылку по системному каналу на PROD (инцидент 2026-07-24, в канале тогда было 24 тысячи участников). Постановка в очередь не задерживает доставку сообщения.

Текст превью строит та же функция, что для пушей (вынести из тела цикла в общий хелпер): «🖼 Фото», «📎 Файл», «📊 Опрос», служебные сообщения расшифрованы через `systemMessagePushText`.

### Содержимое

```json
{
  "id": "evt_<messageId>_<talerUserId>",
  "type": "message.created",
  "createdAt": "2026-10-01T10:00:00.000Z",
  "recipient":    { "externalId": "…", "talerUserId": "…" },
  "conversation": { "id": "…", "type": "DIRECT", "title": null },
  "message": {
    "id": "…",
    "senderTalerUserId": "…",
    "senderExternalId": "…",
    "senderName": "Іван Петренко",
    "preview": "до 200 символов",
    "kind": "text",
    "mentionsRecipient": false,
    "createdAt": "…"
  }
}
```

- `id` детерминирован (сообщение + получатель) — по нему nadi отбрасывает дубли.
- `conversation.title` — имя группы, для личного чата `null`.
- `senderExternalId` — `null`, если пишет человек не из этого партнёра.
- `kind`: `text | image | video | audio | file | system`.

Событие `ping` (от `/webhooks/test`) — `{id, type:'ping', createdAt}`.

### Доставка

- Очередь BullMQ `partner-webhooks` (Redis-подключение уже настроено глобально).
- `POST` с `Content-Type: application/json`, таймаут 5 с, успех — любой `2xx`.
- До 6 повторов с паузами 10 с → 30 с → 1 мин → 5 мин → 15 мин → 1 ч, дальше событие выбрасывается: пуш через час бессмыслен, а сообщение человек увидит, открыв чат.
- Порядок не гарантирован.
- Журнал: последние 1000 попыток на партнёра в Redis (событие, попытка, код ответа, ошибка, длительность). Отдаётся `GET /partner/v1/webhooks/deliveries?limit=` (до 200).
- `POST /partner/v1/webhooks/test` отправляет `ping` синхронно и возвращает `{delivered, status, error?, durationMs}`.

### Подпись

Заголовки: `X-TalerID-Event`, `X-TalerID-Delivery: <id>`, `X-TalerID-Signature: t=<unix-время>,v1=<hex HMAC-SHA256(секрет, "<t>.<сырое тело>")>`. nadi отвергает запрос, если подпись не сходится или `t` отличается от текущего времени больше чем на 5 минут. Секрет вебхука хранится в `Partner` зашифрованным через `encryptSecret`/`decryptSecret` (`src/mail/mail-crypto.ts`) отдельным ключом `PARTNER_SECRETS_KEY` (hex) из env; ключ почтовых ящиков не переиспользуется.

### Не делаем в первой версии

События о прочтении, правках, изменениях в группах (с открытым приложением они приходят через сокет); счётчик непрочитанных в событии; защита от двойного пуша у тех, у кого стоят оба приложения; событие об отзыве связки (nadi узнаёт по `410` на `/token`).

## Данные

Новые модели Prisma (одна миграция):

- **`Partner`** — `id`, `slug` (уникальный), `name` (для писем: «Nadi»), `keyHash` (sha256 ключа), `ipAllowlist String[]`, `webhookUrl?` (только https), `webhookSecretEnc?`, `oauthClientId` (уникальный; клиент `nadi-partner` в `OAuthClient`: `verifiedPartner=true`, `allowedScopes=['messenger']`, без redirect URI), `enabled`, даты.
- **`PartnerLink`** — `id`, `partnerId`, `externalId`, `userId`, `status` (`PENDING|ACTIVE|REVOKED`), `grantId?`, `codeHash?`, `codeExpiresAt?`, `codeAttempts`, `activatedAt?`, `revokedAt?`, даты. Уникальные: `(partnerId, externalId)`, `(partnerId, userId)` — повторная привязка переиспользует строку. Ограничения отправки кода (раз в 60 с, 5 в час) — счётчиками в Redis с TTL, не в БД.
- **`PartnerContact`** — `partnerId`, `userAId`, `userBId` (упорядочены), `createdContact` (контакт создал партнёр или он был раньше), дата. Уникальный `(partnerId, userAId, userBId)`.
- **`BlockedUser.hadContact Boolean @default(false)`** — для исправления разблокировки.
- **`User.createdByPartnerId String?`** (FK на `Partner`, `Restrict`) — какой партнёр завёл аккаунт; вместе с отсутствием пароля определяет управляемый аккаунт.

Правка вне Prisma: scope `messenger` добавляется в список scopes OIDC-провайдера (`oidc-provider.factory.ts`) через константу, по образцу `MCP_SCOPES`.

Грант: **один на связку**, `grantId` хранится в `PartnerLink`. Гранты в Redis живут 30 дней — если грант истёк, `/token` создаёт новый и обновляет `grantId`. Токены выпускаются так же, как в `PartnerService.mintTokens` (`provider.AccessToken`), но без refresh-токена: бэкенд nadi просто запрашивает новый access-токен.

## Безопасность

- Ключ партнёра показывается один раз при выпуске, хранится хэшем, сравнение — за постоянное время. Смена ключа — скриптом; каждая нода держит снимок партнёров до 30 с, поэтому новый ключ начинает, а старый перестаёт работать в пределах этого окна — партнёр меняет ключ с запасом в минуту. Секрет скрипт пишет только в файл 600, открытый до изменения базы: ошибка пути не оставит партнёра без ключа.
- Белый список IP партнёра проверяется по тому же определению адреса клиента, что и остальной бэкенд за nginx/LB; на DEV и PROD проверить, что видится именно адрес сервера nadi.
- Партнёр не может: читать чаты чужого существующего аккаунта без кода из письма; снять блокировку; завести контакт с кем-то вне своих связок; переименовать или удалить неуправляемый аккаунт; выпустить токен, который пустит куда-то кроме открытых ручек мессенджера.
- Все изменяющие действия партнёрского API (создание, привязка, код, отзыв, удаление, контакты) явно пишутся в `AuditLog` с партнёром, `externalId` и действием; неудачные попытки кода — тоже.
- Суточный потолок партнёра на письма с кодом и проверки кода ограничивает перебор по многим аккаунтам при утёкшем ключе.
- Для nadi (в документации): политика конфиденциальности nadi должна говорить, что переписка работает на Taler ID и для этого создаётся аккаунт; nadi отвечает за проверку почты до вызова `POST /users`.

**Принятые риски:**
- Партнёр узнаёт, есть ли у почты аккаунт TalerID (ответ `confirmation_required`). Допустимо для доверенного партнёра.
- Привязанный по коду существующий аккаунт отдаёт партнёру все свои личные чаты и группы, включая переписку с людьми не из nadi. Это прямо сказано в письме с кодом.

## Тестирование

**Юнит-тесты (jest):** разбор и проверка ключа, IP, выключатели; все переходы связки (новая почта, занятая, повтор, `REVOKED` → снова); регистронезависимый поиск почты; лимиты и сгорание кода; пересоздание истёкшего гранта; `MessengerAuthGuard` (свой токен / партнёрский / закрытая ручка / выключенный партнёр); сокет — партнёрский вход, отказ в `call_*`, отключение по истечении; фильтр типов бесед; правило групп; оба исправления; скрытие из поиска; отзыв связок при удалении аккаунта; вебхук — условия постановки (открытый чат, «без звука», упоминание, «тихое», канал, отправитель), единая загрузка связок, подпись, расписание повторов.

**E2E-набор `test:partner` в `taler_id_tests`** (`test:partner` — DEV, `test:partner:prod` — TEST, короткий прогон на PROD — после выкатки): партнёр `e2e`, ключ в `.env` набора.
1. Двое новых пользователей со случайной почтой → `active`, повтор → `created:false`.
2. Токены → оба сокета подключаются, `/profile` с партнёрским токеном → `401`.
3. Без контакта личка не создаётся → `PUT /contacts` → создаётся → сообщение доходит `new_message`.
4. Группа из контакта создаётся; добавление не-контакта → `403`.
5. Получатель не в чате → событие в приёмнике `PARTNER_WEBHOOK_SINK`, подпись сходится.
6. Запреты: `/users/search`, запрос в контакты, `call_invite`, беседа не того типа.
7. Путь «почта занята»: аккаунт с тестовым ящиком на нашем Mailcow `@talerid.io` → `confirmation_required` → `link-code` → код читается по IMAP → `verify` → `active`; неверный код уменьшает `attemptsLeft`.
8. `DELETE /users/{id}` → токен и сокет гаснут сразу.
9. Уборка: `DELETE ?deleteAccount=true` для всех созданных аккаунтов.

Приёмник `PARTNER_WEBHOOK_SINK` — служебная ручка, включаемая только env-переменной (DEV/TEST); хранит последние события партнёра `e2e` в Redis и отдаёт их этому же партнёру. На PROD не включается.

Когда набор стабилизируется, он добавляется в обязательный список тестов перед деплоем в CLAUDE.md.

## Вне рамок

- Бэкенд и приложение nadi.
- Синхронизация аватаров.
- Звонки для партнёров.
- Экран «подключённые приложения» в TalerID, где человек сам отзывает доступ.

- В группу приложения TalerID можно добавить кого угодно без согласия — существующее поведение, не меняем.
- Перенос Linkeon на новый модуль.
- Принцип «Assistant-first» не применяется: новой пользовательской функции в TalerID нет.
