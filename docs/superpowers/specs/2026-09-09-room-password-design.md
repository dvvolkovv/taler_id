# Пароль на встречу: ввод в вебе, задание при создании

Дата: 2026-09-09
Репозитории: `taler_id` (бэкенд, `public/room.html`), `taler_id_mobile`

## Задача

Сделать пароль на встречу доступным человеку. Сегодня механизм есть, но
пользоваться им нельзя: задать пароль можно только запросом к API руками, а
гость по ссылке в браузере ввести его не может вовсе.

## Что есть сейчас

Проверено по коду 2026-09-09.

- `POST /voice/rooms/temporary` и `POST /voice/rooms/public` принимают
  необязательный `password` и хранят его как bcrypt-хеш (`voice.service.ts`,
  `createTemporaryRoom` / `createPublicRoom`).
- `POST /voice/rooms/public/:code/join` (гость) и `…/join-auth`
  (залогиненный) сверяют пароль и отвечают 403 при несовпадении.
- `GET /voice/rooms/public/:code` уже отдаёт `requiresPassword` — вебу не
  нужно угадывать по отказу.
- Мобильное приложение **умеет вводить** пароль при входе по коду: диалог с
  необязательным полем, значение уходит в оба join-эндпоинта.

Чего нет:

- **Задать пароль при создании нельзя нигде.** Календарь
  (`calendar_screen.dart`) и история звонков (`call_history_screen.dart`)
  создают комнату без `password`.
- **Веб-комната пароль не спрашивает.** В `public/room.html` нет ни одного
  упоминания пароля; на 403 показывается «Не удалось подключиться. Попробуйте
  ещё раз» — то есть человек будет жать кнопку бесконечно, потому что
  сообщение говорит о связи, а дело в пароле.
- Освобождение создателя от собственного пароля не выражено решением: оно
  получилось следствием того, что владелец и приглашённые входят другой
  веткой (`joinRoom`), где пароля нет вовсе.

## Решение

Модель доступа не меняется. Работа в трёх точках.

### 1. Веб-комната — ввод пароля

Экран входа уже запрашивает имя и уже загружает описание комнаты. Поле
пароля показывается **только** при `requiresPassword: true` из этого
описания.

Отказ разделяется по причине: 403 — «Неверный пароль», всё остальное —
прежний текст про соединение. Смешивать их нельзя: это разные действия
человека (исправить пароль либо повторить попытку).

Пустое поле при `requiresPassword` не отправляется вовсе — сервер откажет,
а лишний круг только путает.

### 2. Задание пароля при создании

Необязательное поле в обеих точках создания: встреча из календаря и быстрая
комната из истории звонков. По умолчанию пустое, пустое значит «без пароля» —
привычный сценарий не меняется ни на шаг.

После создания комнаты с паролем пароль показывается рядом со ссылкой и
копируется **отдельной** кнопкой. Без этого человек скопирует ссылку,
отправит её и оставит пароль у себя — встреча просто не состоится.

### 3. Создатель не вводит собственный пароль

В `joinPublicRoomAuth` уже есть и `room.creatorId`, и `userId`: проверка
пароля пропускается, если входит создатель.

Приглашённые участники звонка входят веткой `joinRoom`, где пароля нет и не
появится — но это перестаёт быть случайностью и записывается правилом:
пароль защищает вход **по коду комнаты**, а не участие в звонке, на который
тебя позвали поимённо.

Гость и любой посторонний с кодом вводят пароль всегда.

## Проверка

- Юнит-тесты бэкенда: создатель проходит без пароля; чужой залогиненный с
  кодом — не проходит; гость с верным паролем проходит; с неверным получает
  403. Мутировать: снять освобождение создателя, снять сверку пароля.
- E2E: в наборе `room_chat_test.ts` уже есть вход по коду — защищённая
  комната добавляется туда, отдельный набор заводить незачем.
- Веб проверяется руками: комната с паролем и без; верный и неверный пароль;
  сообщение об ошибке соответствует причине.

## Вне объёма

Смена пароля у существующей комнаты (потребовала бы новой ручки — сегодня
пароль задаётся только при создании), пароль внутри ссылки-приглашения,
одноразовые приглашения.

Отдельно названо, а не забыто: **счётчика попыток ввода нет и не
добавляется**. Единственное ограничение сегодня — общий потолок сервиса
(10 запросов в секунду, 100 в минуту с адреса). Для пароля, который человек
диктует голосом или шлёт отдельным сообщением, это приемлемо; если пароли
станут длинными и постоянными, к этому придётся вернуться.
