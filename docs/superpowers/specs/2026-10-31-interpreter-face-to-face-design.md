# Разговор с переводом: двое рядом, у каждого свой телефон — Design

**Date:** 2026-10-31
**Status:** Approved (design), pending implementation plan
**Scope:** бэкенд (`src/interpreter/`, биллинг), агент (`livekit-agent/interpreter.js` и помощники), мобильное приложение (`lib/features/interpreter/` в `taler_id_mobile`), сквозные наборы в `taler_id_tests`. Переводчик в звонках (`livekit-agent/translator.js`) и переводчик ассистента «один телефон на столе» по поведению не меняются.

## Цель

Двое с аккаунтами TalerID сидят рядом, у каждого свой телефон. Каждый говорит на своём языке и слышит в трубке или наушниках **только перевод** речи собеседника — синхронно, без живого голоса собеседника из телефона. Система различает голоса: в перевод уходит только речь владельца телефона. Голос собеседника, долетевший до чужого микрофона, и голоса посторонних не переводятся.

## Контекст: что есть сегодня

- **Переводчик в звонке** (`livekit-agent/translator.js`). Агент входит как `voice-translator` и на каждого говорящего открывает сессии `gpt-realtime-mini`, по одной на целевой язык.
  - Переводит фразами: RMS-детектор, коммит после 600 мс тишины, принудительно через 7 с.
  - Публикует одну общую дорожку `translation-<lang>` на язык. Голос выбирается по языку (`LANG_VOICES`), а не по говорящему.
  - Клиент приглушает собеседника до 0.15 (`voice_call_screen.dart:4276-4298`), и только у того, кто включил перевод. При ответе через CallKit комната подключается с `autoSubscribe: true` и играет все `translation-*` в полную громкость.
  - Субтитров нет, тарификации нет.
  - `translator/start|stop|set-lang` закрыты только `JwtAuthGuard` и не проверяют участие в комнате; `translator/status` открыт без авторизации.
- **Переводчик ассистента** (`translator_prompt.dart`). Один телефон на столе, направление перевода модель выбирает по языку реплики.
- **Сверка голоса.** Сервис `voice-embed-service` (ECAPA, вектор на 192 измерения): `POST /embed` (multipart WAV) → `{vector}`.
  - На DEV и TEST слушает `127.0.0.1:18082`, на PROD — `10.130.0.12:18082` на `do-media`. Во всех трёх окружениях это та же машина, где работает агент.
  - Образец владельца хранится в `Profile.ownerEmbedding` (`Float[]`). Записывается в приложении: `lib/features/voice_enrollment/`, 15 с, WAV 16 кГц, `POST /voice-gate/enroll`.
  - Сейчас сверкой пользуется только realtime-прокси ассистента, с порогом `OWNER_VOICE_THRESHOLD=0.25`.
- **`gpt-realtime-translate` (OpenAI)** — потоковый синхронный перевод.
  - Адрес: `wss://api.openai.com/v1/realtime/translations?model=gpt-realtime-translate`. Одна сессия переводит в одну сторону.
  - Язык источника определяет сама, входных языков больше 70.
  - На выходе 13 языков: en, es, pt, fr, ja, ru, zh, de, ko, hi, id, vi, it.
  - Голос перевода повторяет тон и высоту голоса говорящего. Выбора голоса и промпта нет.
  - Стоимость $0.034 за минуту поданного аудио.
  - Клиент шлёт `session.update` (`session.audio.output.language`), `session.input_audio_buffer.append`, `session.close`.
  - Сервер шлёт `session.created`, `session.output_audio.delta`, `session.output_transcript.delta`, `session.input_transcript.delta`, `session.closed`, `error`.
  - Формат PCM16, моно, 24 кГц. Тишину между фразами тоже подаём.
- **QR в приложении.** Генерация — `qr_flutter` (в профиле `talerid://user/<id>`), сканер — `mobile_scanner`, обработчик схемы `talerid://` — в `lib/core/url_scheme/`.
- **Биллинг:**
  - `GatingService.startSession/endSession`;
  - `MeteringService` — списание каждые 10 с для `MINUTE_BASED`, потолок `MAX_SESSION_HOURS`, при `billingEnforced` сессия закрывается как `terminated_no_funds`;
  - прайс — таблица `AiPricebook`.

## Ключевые решения

| Вопрос | Решение |
|---|---|
| Сценарий | Двое **рядом**, у каждого свой телефон. Звонок на расстоянии в эту работу не входит |
| Как телефоны соединяются | **QR-код**: А показывает, Б сканирует. Контакты и Bluetooth не используются |
| Как различать голоса | **Отпечаток голоса**: сверка с образцами обоих. Образец обязателен для обоих |
| Что звучит в трубке | **Только перевод** речи собеседника. Живой голос собеседника на телефон не передаётся вообще. Громкая связь в этом режиме запрещена |
| Движок перевода | `gpt-realtime-translate`, если пара ему по силам. Иначе фразовый движок на полной `gpt-realtime` |
| Кто платит | **Тот, кто начал** (показал QR), за оба направления, поминутно. Новая статья прайса `interpreter` |
| Где в приложении | Вкладка «Звонки», кнопка «Разговор с переводом». Плюс инструмент ассистента `open_interpreter` |
| Платформы | iOS и Android. Десктоп не делаем |
| Шифрование | Сквозного шифрования в режиме нет: перевод выполняется на сервере. На экране есть пометка |
| Существующие переводчики | Не трогаем. Новый модуль живёт рядом |

## Пользовательский сценарий

### Вход в раздел
- Вкладка «Звонки» (`call_history_screen.dart`): кнопка «Разговор с переводом» в одном ряду с «Создать встречу». Кнопка видна, только если сервер поддерживает режим (см. «Выключатель»).
- Ассистент: инструмент `open_interpreter({action: 'host' | 'join'})` открывает экран старта или сканер. Инструменты ассистента объявляются в приложении (`assistant_tools_schema.dart`), поэтому он делается вместе с экранами; на бэкенде — только упоминание в промптах `src/assistant/prompts/`.

### Образец голоса
Если у пользователя нет образца (`GET /voice-gate/owner-status`), перед стартом и перед входом открывается существующая шторка `owner_enrollment_sheet.dart`. Без образца дальше пройти нельзя. Сервер проверяет то же самое и отвечает `409 voice_print_required`; на этот ответ приложение тоже открывает шторку записи, а не только показывает текст.

Образец считается, только если `ownerEmbedding` — 192 конечных числа и сумма их квадратов конечна и больше нуля (не `Math.hypot`: тот сам масштабирует и пропустит векторы, на которых сумма квадратов уходит в 0 или бесконечность); иначе тот же `409`. Агент такой образец не примет (`interpreter-routing.js`), и сессия закрылась бы `translation_failed` уже после открытия биллинга. Агент отклоняет и пару с почти одинаковыми образцами (косинус от 0,99): разные люди так не совпадают, это ошибка сборки участников.

### Старт (А)
1. На экране строка «Я говорю на: <язык> ▾». По умолчанию стоит язык приложения, последний выбор хранится на телефоне; в профиль ничего не пишем.
2. По кнопке «Начать» уходит `POST /interpreter/sessions`.
3. Появляется крупный QR `talerid://interp/<код>`, обратный отсчёт 5 минут и кнопка «Новый код».
4. А уже подключён к комнате и ждёт собеседника.

### Вход (Б)
1. Б жмёт «Сканировать QR» в том же разделе. Системная камера тоже подходит: она откроет приложение по схеме `talerid://interp/<код>`, как и сканер профиля.
2. Б выбирает «Я говорю на: <язык> ▾».
3. Уходит `POST /interpreter/sessions/join`.

На каждую ошибку — свой понятный текст: код просрочен, код уже использован, код свой, языки совпадают («перевод не нужен»), нет образца голоса, у организатора не хватает средств.

### Разговор
- Телефон у уха или наушники. По умолчанию звук идёт в трубку, при подключённых наушниках — в них. Громкая связь недоступна: перевод из динамика попадал бы в микрофон соседа.
- В трубке звучит только перевод речи собеседника. Своя речь не звучит.
- Когда телефон у уха, экран гаснет по датчику приближения. Когда не у уха, на экране видно:
  - имя и язык собеседника;
  - индикатор того, кто сейчас говорит (по сигналу агента);
  - «собеседник говорит…», пока его перевод ещё не зазвучал;
  - субтитры: перевод речи собеседника и то, как распознана своя речь;
  - у А — таймер и стоимость;
  - пометка «перевод по фразам», если направление идёт фразовым движком;
  - пометка «Перевод идёт через сервер».
- Кнопки «Микрофон» и «Завершить». Выключать микрофон безопасно: мой голос, долетевший до телефона соседа, не пройдёт сверку с его образцом.

### Завершение
- Любой из двоих жмёт «Завершить» → `POST /interpreter/sessions/:id/end` → разговор закрыт у обоих.
- Если кто-то пропал из сети, ждём переподключения 60 с, затем закрываем.
- Итоговый экран показывает длительность, а у А ещё и списанную сумму.

## Архитектура

```
Телефон А ─ микрофон А (подписка только для агента) ─┐                          ┌─ interp-for-Б ─► Телефон Б
                                                     ├─► voice-interpreter ─────┤
Телефон Б ─ микрофон Б (подписка только для агента) ─┘  фильтр голоса → перевод└─ interp-for-А ─► Телефон А
                                                         + субтитры (data, topic `interp`)

бэкенд src/interpreter/ ── POST /interpreter/start|stop ──► агент :3100 ── POST /embed ──► voice-embed-service :18082
            ▲                                                   │
            └────────── POST /interpreter/internal/…/agent-ended ┘        агент ── WSS ──► OpenAI
```

### Бэкенд: модуль `src/interpreter/`

Модуль отдельный, в `voice.service.ts` (2,5 тыс. строк) ничего не добавляем.

**Модель `InterpreterSession`** (новая миграция):

| Поле | Тип | Смысл |
|---|---|---|
| `id` | uuid | |
| `roomName` | string, unique | `interp-<uuid>` |
| `hostId` / `guestId` | uuid / uuid? | А / Б |
| `hostLang` / `guestLang` | string / string? | ISO 639-1 |
| `codeHash` | string?, unique | sha256 действующего кода; после входа Б — `null` |
| `codeExpiresAt` | дата-время? | |
| `status` | enum `waiting`, `active`, `ended` | |
| `billingSessionId` | uuid? | `AiSession.id` |
| `agentSeenAt` | дата-время? | когда сверка последний раз видела агента в комнате; по нему считается `agent_lost` |
| `startedAt` / `endedAt` | дата-время? | `startedAt` — момент входа Б |
| `endReason` | enum? | `hangup`, `partner_left`, `no_funds`, `max_duration`, `translation_failed`, `agent_lost`, `expired` |
| `createdAt` / `updatedAt` | дата-время | |

Статус и причина завершения — enum-ы Prisma в верхнем регистре (как во всей схеме), в API отдаются в нижнем.

**Ручки.** Все под `JwtAuthGuard`, кроме внутренней. Каждая проверяет, что вызывающий — участник именно этой сессии.

Ошибка — код snake_case в `message`, как во всём бэкенде (глобальный фильтр пересобирает тело и `code` не сохранил бы):

| Код | Когда |
|---|---|
| `403 interpreter_disabled` | выключатель выключен |
| `400 unsupported_language` / `400 same_language` | язык не из списка / совпадает с языком хоста |
| `409 voice_print_required` / `409 host_voice_print_required` | нет пригодного образца у вызывающего / у хоста |
| `409 already_in_session` | у пользователя уже идёт разговор |
| `402 insufficient_funds` / `403 feature_disabled` | при создании: у самого хоста нет резерва / выключен тумблер |
| `402 host_insufficient_funds` / `403 host_feature_disabled` | при входе Б: то же у хоста |
| `404 code_not_found` / `410 code_expired` / `409 own_code` / `409 code_used` | код |
| `429 too_many_attempts` | больше 10 попыток входа в минуту |
| `503 interpreter_unavailable` | агент не стартовал |
| `404 session_not_found` / `409 not_waiting` | чужая или несуществующая сессия / новый код не в `waiting` |

- `GET /interpreter/languages` → `{enabled, languages: [{code, name}]}`. Список — 81 язык агента, ровно коды `SUPPORTED_LANGS` из `livekit-agent/lang-names.js`, без регионов (`pt`, не `pt-BR`). Импортировать агентский файл в бэкенд нельзя: сборка не кладёт `livekit-agent/` в `dist/`. Поэтому в бэкенде своя копия списка и Jest-тест, который сверяет её с `lang-names.js`. Код, который бэкенд примет, а агент нет, закончится `503` уже после открытия биллинга. Синхронность зависит от пары и сообщается при входе Б.
- `POST /interpreter/sessions` с телом `{lang}`. Проверки:
  - режим включён;
  - язык поддерживается;
  - у пользователя есть образец голоса;
  - нет сессии в статусе `active` (`409 already_in_session`). Своя сессия в `waiting` закрывается как `hangup`: новый старт заменяет старый QR;
  - резерв на `interpreter` есть. Проверяет новый `GatingService.assertCanStart` — те же проверки, что в `startSession`, но без открытия биллинг-сессии: `startSession` сразу начал бы списание. При `billingEnforced=false` — только запись в лог.

  Создаёт комнату LiveKit `interp-<uuid>` с `maxParticipants: 4` (двое, агент и запас на переподключение), `departureTimeout: 60` и строку `InterpreterSession` в статусе `waiting`. Генерирует код: 8 символов base32 без похожих букв, живёт 5 минут. Ответ: `{sessionId, code, expiresAt, roomName, token, livekitWsUrl}`.

  Токен участника:
  - публиковать можно только микрофон (`canPublishSources: [MICROPHONE]`), подписка разрешена;
  - identity — `makeParticipantIdentity(userId, <id сессии входа>)`, как у звонков: человек плюс устройство;
  - в metadata — `{lang}`.
- `POST /interpreter/sessions/:id/code` — новый код. Только для хоста и только в статусе `waiting`; прежний код гаснет.
- `POST /interpreter/sessions/join` с телом `{code, lang}`. Проверки:
  - режим включён;
  - код найден по хэшу, не истёк, сессия в статусе `waiting`;
  - входит не хост;
  - язык поддерживается и отличается от `hostLang`;
  - у Б есть образец голоса.

  Действия строго по порядку:
  1. Открывает `GatingService.startSession(hostId, 'interpreter', contextRef=sessionId)`. Если при `billingEnforced` у хоста не хватает средств, ответ `402 host_insufficient_funds` (выключен тумблер — `403 host_feature_disabled`), и в сессии ничего не меняется: она остаётся `waiting`, код по-прежнему действует. Исключения биллинга — обычные `Error`, без перехвата они стали бы `500`.
  2. В одной транзакции, с условием `status = 'waiting'` (защита от двух одновременных входов по одному коду), записывает `guestId`, `guestLang`, `billingSessionId`, ставит `status=active` и `startedAt`, гасит код. Если транзакция не прошла, биллинг-сессия из шага 1 закрывается, ответ `409 code_used`.
  3. Вызывает `POST {AI_AGENT_URL}/interpreter/start`, тело — в разделе «Агент». Если агент не стартовал, биллинг закрывается, сессия получает `ended/translation_failed`, Б видит ответ `503 interpreter_unavailable`.

  Вызовы агента идут с заголовком `x-interpreter-secret`, с таймаутами (`start` — 35 с, `stop` — 10 с, `selftest` — 25 с) и с проверкой `res.ok`. Векторы образцов не попадают ни в логи, ни в тексты ошибок.

  Успешный ответ Б: `{sessionId, roomName, token, livekitWsUrl, partner: {firstName, avatarUrl, lang}, directions: {toMe: 'simultaneous'|'phrase', fromMe: 'simultaneous'|'phrase'}}`.
- `GET /interpreter/sessions/:id` → `{status, endReason, partner, directions, startedAt}`. А узнаёт о входе Б из события LiveKit (подключился участник); эта ручка — запасной путь и источник причины завершения.
- `POST /interpreter/sessions/:id/end` (идемпотентна). Останавливает агента (`POST /interpreter/stop`), закрывает биллинг, удаляет комнату (`deleteRoom`), ставит `status=ended`.
- `POST /interpreter/internal/sessions/:id/agent-ended` с телом `{reason}` — агент сообщает, что остановился сам. Защищена заголовком `x-interpreter-secret`, по образцу `x-recorder-secret`. Закрывает биллинг, удаляет комнату, ставит `ended` с причиной от агента. Идемпотентна: после сетевой ошибки или 5xx агент повторяет вызов один раз, поэтому вызов для уже закрытой сессии ничего не меняет и отвечает 200.

**Периодическая сверка** раз в 10 с, по образцу `MeteringService`:
- Активная сессия, чья биллинг-сессия уже не `active` (`terminated_no_funds` или `terminated_stale`), закрывается с причиной `no_funds` или `max_duration`.
- Активная сессия, в комнате которой участника `voice-interpreter` нет дольше 60 с (`listParticipants`), закрывается с причиной `agent_lost`. Так ловятся рестарт и деплой агента: в этих случаях он сам `agent-ended` не пришлёт. Отсчёт идёт от `agentSeenAt` (а до первой сверки — от `startedAt`). Если `listParticipants` упал, сверка в этот раз ничего не делает: сбой API — не пустая комната.
- Сессия в `waiting`, у которой код истёк больше 5 минут назад и новый не запрошен, закрывается с причиной `expired`.

Каждое закрытие по сверке идёт тем же путём, что и `end`: стоп агента, закрытие биллинга, удаление комнаты. Закрытие условное (`status ≠ ended` → `ended`), поэтому из двух app-нод PROD побочные действия выполняет одна. Биллинг закрывается, только если `AiSession` ещё `active` (`endSession` не идемпотентен): `translation_failed` и `agent_lost` — как `failed`, `no_funds` и `max_duration` — уже закрыт метерингом, остальное — `completed`.

**Безопасность:**
- Векторы образцов никакая ручка не отдаёт и в логи не пишет. Агенту они уходят только по внутренней сети: localhost на DEV и TEST, VPC `10.130.0.0/20` на PROD.
- Перебор кодов: около 40 бит, TTL 5 минут, код одноразовый. На ручку входа — 10 попыток в минуту на пользователя, счётчиком в Redis. `@Throttle` для этого не годится: глобальный `ThrottlerGuard` считает по IP и срабатывает раньше проверки токена.
- `RoomAccessGuard` пускает любой токен LiveKit своей комнаты на ручки записи встречи, публичного переводчика и чата. Для комнат `interp-*` он отвечает `403 interpreter_room`: иначе участник разговора с переводом мог бы своим токеном включить в нём запись встречи.

**Выключатель** `INTERPRETER_ENABLED` (по умолчанию выключен). В выключенном состоянии `languages` отвечает `enabled=false`, остальные ручки — `403 interpreter_disabled`. Приложение показывает кнопку только при `enabled=true`.

### Биллинг

- `FEATURE_KEYS.INTERPRETER = 'interpreter'`. Добавить в `MINUTE_BASED`, в `MAX_SESSION_HOURS` выставить 2.
- Миграция добавляет строку `AiPricebook`: `interpreter`, единица — минута, себестоимость $0.07 (два синхронных потока по $0.034). Наценка общая, ×2, то есть клиент платит около $0.14 в минуту, примерно 12 μTAL. Минимальный резерв — 2 минуты. Цена правится админской ручкой прайса без релиза.
- Платит хост. Биллинг-сессия открывается при входе Б и закрывается при любом завершении. Ожидание на экране QR не тарифицируется.
- `interpreter` появляется в «тумблерах ИИ», с подписью на ru и en.

### Агент: `livekit-agent/interpreter.js` и помощники

Работает в том же процессе `livekit-ai-agent`, ручки на `:3100`. Все ручки требуют заголовок `x-interpreter-secret`.

- `POST /interpreter/start` с телом `{sessionId, roomName, participants: [{userId, lang, embedding}, {userId, lang, embedding}]}` → `{status: 'started' | 'already_running'}`.
  - Комната занимается до первого ожидания. Повторный старт той же комнаты (бэкенд повторил запрос, который не дождался ответа) ждёт первый и отвечает `already_running` или `503`.
  - `503` ещё в двух случаях: сессию остановили, пока она стартовала; у агента нет `OPENAI_API_KEY`.
  - Таймаут бэкенда на этот вызов — не меньше 30 с. Подключение к LiveKit ограничено 15 с; публикация двух дорожек не ограничена, но обычно занимает меньше секунды. Если бэкенд всё же не дождался ответа, его `stop` чисто прерывает незавершённый старт.
- `POST /interpreter/stop` с телом `{roomName}` → `{status: 'stopped' | 'not_running'}`.
- `GET /interpreter/selftest` параллельно открывает сессию `INTERPRETER_MODEL` и сессию фразового движка на `INTERPRETER_FALLBACK_MODEL`, шлёт обеим `session.update` и ждёт подтверждения не дольше 10 с → `{ok, reason, simultaneous, phrase, latencyMs}`. Фразовая модель — датированный снимок: если OpenAI её уберёт, без этой проверки сломанное фразовое направление заметят только пользователи. Бэкенд пробрасывает её как `GET /interpreter/selftest` своего модуля, под `JwtAuthGuard`: в отличие от открытого `translator/selftest`, анонимный вызов не должен открывать сессии OpenAI.

**Сессия разговора:**
1. Агент подключается к комнате как `voice-interpreter`.
2. На каждого из двоих участников (ключ — `baseIdentity`, то есть человек, а не устройство) строится цепочка: подписка на микрофон → `AudioStream` 24 кГц моно → фильтр голоса → направление перевода (на язык собеседника) → дорожка `interp-for-<baseIdentity слушателя>`.
3. Субтитры и сигналы уходят через `publishData`: reliable, topic `interp`, адресно через `destinationIdentities`.

   | Сообщение | Кому |
   |---|---|
   | `{"type":"caption","role":"translation","speaker":"<userId>","text":"…","final":false}` | слушателю |
   | `{"type":"caption","role":"source","speaker":"<userId>","text":"…","final":false}` | говорящему |
   | `{"type":"speaking","speaker":"<userId>","on":true}` | обоим |
   | `{"type":"status","state":"reconnecting"\|"ok"\|"failed"}` | обоим |

   Субтитры от синхронного движка приходят дельтами (`final:false`). На строки их разбивает клиент: новая строка начинается, если дельт не было 1,2 с. Перевод отстаёт от речи на секунды, поэтому закрывать строку по концу речи нельзя: хвост перевода начал бы новую строку. Фразовый движок шлёт фразу целиком с `final:true`.

   Сигнал `speaking` берётся с выхода фильтра, то есть с задержкой фильтра. Сигнал на входе, до сверки, показал бы «собеседник говорит», когда это мой голос долетел до его микрофона.
4. Агент останавливается и шлёт `agent-ended` в трёх случаях:
   - участник отсутствует 60 с подряд → `partner_left`;
   - перевод не восстановился → `translation_failed`;
   - получен `stop` от бэкенда (колбэк не нужен).

**Фильтр голоса — `livekit-agent/voiceprint-gate.js`**

- Аудио режется на куски по `INTERPRETER_GATE_CHUNK_MS` (по умолчанию 500 мс). Через фильтр проходит всё аудио, и речь, и тишина, порядок сохраняется. Кусок выпускается, только когда готов следующий: тот нужен для окна. Поэтому задержка — около двух кусков, то есть ~1 с.
- Кусок без речи (RMS ниже `INTERPRETER_SPEECH_RMS`, по умолчанию 400, как в `translator.js`) уходит дальше настоящей тишиной, нулями. Модели нужен непрерывный поток, а тихий голос соседа ниже порога речи для неё всё равно разборчив и попал бы в перевод.
- Кусок с речью проверяется:
  1. Берётся окно 1,5 с: предыдущий кусок, сам кусок и следующий.
  2. Окно оборачивается в WAV на родных 24 кГц и отправляется в `POST {VOICE_EMBED_URL}/embed`. До 16 кГц сервис приводит сам — так же с ним работает realtime-прокси ассистента.
  3. Считаются косинусы вектора с образцом владельца телефона (`s_own`) и с образцом собеседника (`s_other`).
- Правило пропуска: `s_own ≥ τ` и `s_own − s_other ≥ δ`, где `τ = INTERPRETER_VOICE_THRESHOLD` (по умолчанию 0.2) и `δ = INTERPRETER_VOICE_MARGIN` (по умолчанию 0.05). Значения выставлены по стенду 01.11.2026 (`livekit-agent/bench/reports/`). Однословный ответ похож на свой образец всего на 0,24–0,31, поэтому τ = 0,37 отсекал бы все такие ответы. Своих от чужих отделяет зазор δ: у своей речи он не ниже 0,14, у голоса собеседника и эха — не выше −0,29. Посторонний третий голос стенд не проверял — это ручная проверка на телефонах. Кусок, не прошедший проверку, заменяется тишиной той же длины.
- Сглаживание (`INTERPRETER_GATE_HYSTERESIS`, по умолчанию 2):
  - первый кусок новой речи (после куска тишины) должен пройти проверку сам;
  - внутри непрерывной речи кусок, проваливший проверку, всё равно пропускается, если подряд провалились меньше двух кусков;
  - начиная со второго провала подряд куски заменяются тишиной, пока какой-то кусок снова не пройдёт.

  Цена сглаживания — до 0,5 с голоса соседа, если он вступил без паузы сразу после владельца. Эту утечку гасит вторая линия защиты (см. «Сбои»).
- Короткие реплики («да», «нет», «ок») идут по тому же правилу. На стенде их проверяют отдельно.
- Если сервис не ответил за `INTERPRETER_GATE_TIMEOUT_MS` (по умолчанию 300) или вернул ошибку, кусок пропускается без проверки (fail-open). Агент ведёт счётчик и пишет в лог `[INTERPRETER] gate fail-open`. Если fail-open длится больше 60 с подряд, пишется строка `FATAL interpreter: voice-embed unavailable`.
- Векторы держатся только в памяти сессии и в логи не попадают.
- Итоговая добавка к задержке — около 1 с плюс время ответа сервиса, не больше 300 мс.

**Направление перевода**

- Выбор движка — `livekit-agent/interpreter-langs.js`. Синхронный движок выбирается, если язык слушателя входит в 13 выходных языков модели **и** язык говорящего входит в её входные языки. Оба списка — константы, сверенные с документацией OpenAI.
- Синхронное направление — модуль `livekit-agent/translate-session.js`:
  - WSS `…/v1/realtime/translations?model=${INTERPRETER_MODEL}`, заголовки `Authorization` и `OpenAI-Safety-Identifier` (хэш id говорящего);
  - `session.update` с `{session: {audio: {output: {language: <lang>}}}}`;
  - непрерывная подача `session.input_audio_buffer.append`: base64 PCM16 24 кГц, порциями по 100 мс, тишина тоже;
  - `session.output_audio.delta` → дорожка слушателя;
  - `session.output_transcript.delta` → субтитр слушателю;
  - `session.input_transcript.delta` → субтитр говорящему.

  - в том же `session.update` — расшифровка входа (`audio.input.transcription`, модель `gpt-4o-mini-transcribe`) и шумоподавление `near_field`; без расшифровки `session.input_transcript.delta` не приходит вовсе.

  Проба на DEV (`livekit-agent/bench/PROBE.md`) подтвердила: поля событий — `delta`; `session.updated` приходит, а до него сессия переводит на испанский; на речи, уже на языке перевода, модель молчит (0,0 с озвученного звука на ru→ru и de→de).
- Остальные пары идут фразовым движком. `createRealtimeSession` вместе с соседними помощниками переносится из `translator.js` в `livekit-agent/realtime-phrase-session.js`. Туда же уезжают таблицы языков (`lang-names.js`) и вывод звука (`audio-out.js`). `translator.js` импортирует их оттуда, его поведение не меняется. Функция получает необязательные параметры:
  - `model` — по умолчанию прежняя `gpt-realtime-mini`, поэтому переводчик в звонках не меняется;
  - `onTranscript` — для субтитров;
  - `pruneHistory` — по умолчанию выключен;
  - `wsFactory` — для тестов;
  - `onServerError` — ошибки от OpenAI, уже записанные в журнал;
  - `logText` — `false` пишет в журнал длину реплики вместо её слов.

  Обёртка `phrase-session.js` приводит фразовый движок к тому же виду, что и синхронный, и на сбоях ведёт себя так же:
  - если подтверждения настроек нет 10 с, OpenAI отказал в `session.update` или в буфере сокета больше 1 МБ, сокет обрывается как неожиданно закрытый;
  - звук до подтверждения ждёт не больше 4 с;
  - уходит заголовок `OpenAI-Safety-Identifier`;
  - реплики в журнал не пишутся.

  Переподключения у обоих движков общие — `reconnecting-engine.js`.

  Разговор с переводом передаёт `model = INTERPRETER_FALLBACK_MODEL` (по умолчанию `gpt-realtime-2025-08-28`: mini наполовину переводит родственные языки, это ловили на словацком в 1.1.35), известный язык источника вместо `auto` и `pruneHistory: true`. С этим флагом агент удаляет (`conversation.item.delete`) элементы реплики, чей перевод уже озвучен, то есть после её `response.done`. Реплики, ещё стоящие в очереди, не трогаются. Без этого контекст и стоимость растут весь разговор.
- Если сокет к OpenAI оборвался, агент пробует переподключиться до 3 раз, с паузами 1, 2 и 4 с, и шлёт `status: reconnecting`. Не удалось — `status: failed`, стоп и `agent-ended` с причиной `translation_failed`.
- Громкость перевода — `INTERPRETER_GAIN`, по умолчанию 1.4, как `TRANSLATOR_GAIN`.

**Дорожки и подписки:**
- **Живой микрофон закрыт на сервере.** Клиент сразу после подключения, до публикации микрофона, вызывает `setTrackSubscriptionPermissions(allParticipantsAllowed: false, trackPermissions: [ParticipantTrackPermission(voice-interpreter, allTracks)])` (метод есть в `livekit_client` 2.4.1). После этого сервер LiveKit не даст собеседнику подписаться на чужой микрофон.
- **Дорожки перевода изолированы иначе.** `@livekit/rtc-node` 0.13 не умеет ограничивать подписку на собственные дорожки, поэтому здесь изоляция держится на имени `interp-for-<слушатель>` и фильтре клиента. Ошибка клиента дала бы человеку перевод его же речи, но не живой голос собеседника.
- Если слушатель переподключился с другого устройства, он получает ту же дорожку: ключ — человек.

### Мобильное приложение: `lib/features/interpreter/`

Обычная структура фичи: data, domain, presentation; BLoC; GetIt. В `voice_call_screen.dart` (6,9 тыс. строк) ничего не добавляем.

- `InterpreterRemoteDataSource` — `languages`, `create`, `newCode`, `join`, `get`, `end`.
- `InterpreterRoomController` — своя логика комнаты, без общих со звонком циклов «подписаться на всё»:
  - подключение с `autoSubscribe: false`;
  - права на микрофон только для `voice-interpreter`, выставленные до публикации;
  - подписка только на `interp-for-<я>` от `voice-interpreter`; остальное игнорируется, в том числе при переподключении;
  - разбор сообщений topic `interp`;
  - маршрут звука: трубка или наушники, громкая связь заблокирована;
  - датчик приближения.
- `InterpreterBloc`: `needVoicePrint → choosingLanguage → hosting(code, expiresAt) | joining → connecting → active(partner, directions, captions, speaking, status) → ended(reason)`, плюс `error(kind)`.
- Экраны: `InterpreterStartScreen` (язык, «Начать», «Сканировать QR»), `InterpreterQrScreen`, сканер на `mobile_scanner`, `InterpreterSessionScreen`.
- Маршруты `/dashboard/interpreter` и `/dashboard/interpreter/join/:code`. Путь `talerid://interp/<код>` добавляется в `lib/core/url_scheme/` и в сканер профиля.
- Ассистент: инструмент `open_interpreter` в `assistant_tools_schema.dart` и `assistant_tools_executor.dart`, строки в промптах ru и en.
- Все тексты — в ARB ru и en.
- **iOS.** Разговор с переводом не идёт через CallKit. Нужно убедиться, что `CallKitAudioBridge.swift` не включает ручной режим звука WebRTC для комнат `interp-*`. Аудиосессия — `.playAndRecord` / `.voiceChat` (трубка), как у звонка без CallKit.
- **Android.** Проверить, держит ли микрофон в фоне тот же foreground service, что у звонков. Если не держит — подключать его на время разговора.

## Сбои и крайние случаи

| Ситуация | Поведение |
|---|---|
| Сервис сверки не отвечает | Fail-open по кускам, лог; через 60 с — строка `FATAL` для мониторинга. Вторая линия защиты: голос собеседника уже на языке перевода, а на такой речи модель молчит — проба на DEV показала 0,0 с озвученного звука на ru→ru и de→de |
| Обрыв сокета к OpenAI | 3 попытки, на экране «перевод восстанавливается…»; затем завершение `translation_failed` и остановка счётчика |
| Телефон потерял сеть | LiveKit переподключается сам; через 60 с отсутствия — `partner_left` у обоих |
| Перевод из трубки попал в свой микрофон | Обычно гасит AEC телефона. Если просочится, сверку не пройдёт: голос похож на собеседника, а не на владельца |
| Посторонний голос рядом | Не похож ни на один образец, не переводится |
| Оба говорят одновременно | Направления независимы, оба переводятся |
| Короткие «да / нет / ок» | Общее правило; на стенде проверяются отдельно |
| QR просрочен, использован или свой | Понятное сообщение; хост может показать новый код, не начиная заново |
| У хоста кончились деньги (`billingEnforced`) | Сверка видит закрытую биллинг-сессию → `no_funds` у обоих |
| Разговор дольше 2 часов | Счётчик закрывается сам → `max_duration` |
| Деплой или рестарт агента | Идущие разговоры рвутся, как сейчас у переводчика. Клиент видит уход `voice-interpreter` и показывает «перевод прервался»; бэкенд закрывает сессию по сверке (`agent_lost`, когда комната без агента дольше 60 с) |
| Приложение свёрнуто | Как обычный звонок; на Android — foreground service (см. мобилку) |

## Тестирование

**Шаг 0 — стенд на DEV, до экранов.** Скрипт заводит в комнату двух ботов (`@livekit/rtc-node`) с WAV-фикстурами, синтезированными один раз через `say -v Milena` (ru) и `say -v Anna` (de), и запускает агента в режиме разговора с переводом. Замеряем и решаем:
- задержку (от начала речи до первого звука перевода) и качество `gpt-realtime-translate` на парах ru↔de и ru↔en;
- поведение модели на речи, которая уже на языке перевода;
- распределение `s_own` и `s_other` после Opus для трёх случаев: свой голос, голос соседа, перевод из трубки; отдельно для коротких реплик. По итогам выставляем τ, δ и гистерезис;
- нагрузку сервиса сверки на `do-media`-подобном профиле (до 4 запросов в секунду).

Если синхронная модель слаба на русском, это выяснится здесь, и решение о движке пересматривается до экранов.

**Модульные тесты:**

  - `interpreter-langs.test.js` и `interpreter-routing.test.js`: выбор движка по паре, имена дорожек по слушателю;
  - `reconnecting-engine.test.js`, `phrase-session.test.js`, `realtime-phrase-session.test.js`: переподключения, обёртка фразового движка, удаление озвученных реплик;

  - прежние тесты `translator-*.test.js` остаются зелёными: поведение `createRealtimeSession` по умолчанию не меняется.
- Бэкенд (Jest): создание (образец, код и его хэш, одна активная сессия), новый код, вход (просрочен, использован, свой, одинаковые языки, нет образца), проверка участия на всех ручках, открытие и закрытие биллинга, тело команды агенту, секрет колбэка, периодическая сверка.

**Сквозной набор** `test:interpreter` (DEV) и `test:interpreter:prod` (TEST) в `taler_id_tests`, по образцу `test:speakers`:
1. Тестовые аккаунты `integration_test` и `integration_test_2` записывают образцы WAV-фикстурами двух разных синтезированных голосов.
2. А создаёт сессию, Б входит по коду. Оба подключаются ботами и говорят по сценарию с паузами.
3. Проверки:
   - каждый получает только свою дорожку `interp-for-<я>`, и в ней есть звук в нужном окне;
   - субтитры приходят на нужном языке;
   - фраза, проигранная в микрофон А голосом Б, не переводится;
   - биллинг-сессия `interpreter` открыта на А и закрыта после `end`;
   - негативные случаи ручек;
   - уборка: сессии, комнаты, образцы возвращаются к исходным.

Проверку «Б не может подписаться на живой микрофон А» этот набор не выполняет: боты на `@livekit/rtc-node` не умеют выставлять права на свои дорожки. Она покрыта тестом контроллера комнаты и ручной проверкой.

**Пост-деплойный смоук** `test:interpreter-selftest` / `:prod` / `:talerid`: вход тестовым аккаунтом и `GET /interpreter/selftest`. Добавляется в обязательный список CLAUDE.md рядом с `test:translator`.

**Ручная проверка на телефонах.** iPhone и Android, двое разных людей: один человек с двумя аккаунтами даёт почти немую сессию. Его голос похож сам на себя примерно на 0,95, и зазор 0,05 почти ничего не пропускает.
- телефон у уха и AirPods;
- пары ru↔de (синхронно) и ru↔sk (фразами);
- тихий кабинет и кафе;
- короткие ответы и посторонний голос рядом;
- выключенный микрофон, обрыв сети, свёрнутое приложение;
- входящий звонок TalerID или GSM во время разговора;
- субтитры и итоговый экран.

## Выкатка

1. Ветки: `feat/interpreter` от `main` в бэкенде (агент живёт там же) и отдельный worktree в мобилке. Бэкенд `dev` в `main` не сливаем; в `dev` и `main` попадают отдельные слияния фичи.
2. DEV:
   - бэкенд, агент, миграция (таблица и строка прайса); при новой миграции обязательно `npx prisma migrate deploy` и `npx prisma generate`;
   - env на сервере, `INTERPRETER_ENABLED=true`;
   - зелёные наборы;
   - dev-сборки Android и iOS для ручной проверки.
3. TEST, затем PROD — каждый шаг только по явной команде. На PROD агент копируется в `/opt/livekit-agent` на `do-media` (это не git-чекаут; перед заменой сверить `sha256sum`), env выставляется на `do-media` и на обеих app-нодах.
   - Копируются **все** изменённые и новые файлы `livekit-agent/` сразу. `translator.js` теперь импортирует `lang-names.js`, `audio-out.js` и `realtime-phrase-session.js`; если скопировать его одного, агент не стартует целиком — вместе с записью встреч, переводчиком звонков и музыкой ожидания.
   - Перед `pm2 restart livekit-ai-agent` проверить в `/opt/livekit-agent`, что грузится всё, что подключает `index.js` (сервер при этом не поднимается): `node -e "require('dotenv').config(); const s=require('fs').readFileSync('index.js','utf8'); for (const [,m] of s.matchAll(/require\(['\"](\.\/[^'\"]+)['\"]\)/g)) require(m); console.log('modules-ok')"`. Ожидается `modules-ok`. Самопроверка `/translator/selftest` такого не ловит: у неё своя копия настроек сессии.
4. Мобильный релиз по обычным правилам: `/app/version` и `APP_RELEASES`. Объявление — только когда на месте все платформы.
5. Задача плана: проверить, видит ли taler-monitor логи pm2 агента со строкой `FATAL interpreter: …`; если не видит — подключить.

## Вне этой работы

- Звонок с переводом на расстоянии. Позже это добавляется тем же агентом и движками, без фильтра голоса.
- Групповой разговор больше чем на двоих.
- Десктоп.
- Отсев по сравнению громкости микрофонов, без образца голоса. Отклонён в пользу отпечатка голоса; может пригодиться как дополнительный слой.
- Найдено попутно и чинится отдельно:
  - ручки `translator/start|stop|set-lang` не проверяют участие в комнате, `translator/status` открыт без авторизации;
  - переводчик в звонках не тарифицируется;
  - при ответе через CallKit слышны все `translation-*` дорожки;
  - у агента на :3100 без авторизации все прежние ручки (`/join`, `/leave`, `/record`, `/stop-record`, `/translator/*`, `/hold-music/*`), а на некоторых хостах порт виден не только с localhost;
  - битый JSON отсекает глобальный `express.json()` ещё до проверки секрета, и при незаданном `NODE_ENV` в ответ уходит HTML со стеком: нужен обработчик ошибок JSON в `index.js` или `NODE_ENV=production` на агенте;
  - `translator.js` и `recorder.js` читают аудио `for await` из `AudioStream`, а в rtc-node 0.13 такой поток сам не кончается, когда участник уходит: цикл и сессия висят до перезапуска агента. Ревью задачи 16 вывело это из исходников rust-sdks, вживую не проверено. Быстрая проверка на DEV — в журнале переводчика почти нет строк `Audio loop ended` против `Participant disconnected`.
