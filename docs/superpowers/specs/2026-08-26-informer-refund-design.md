# Informer: причина отказа в списке и возврат средств

**Дата:** 2026-08-26
**Источник требований:** `informer-client-changes.md` от команды платформы (admin-API, `gsmsoft1/exchange/admin-api`)
**Затрагивает:** `src/informer-bot/` в бэкенде `taler-id`. Мобильное приложение — без изменений.

## Задача

Платформа добавила два аддитивных изменения в семейство `informer`:

1. В элементах `GET /informer/v1/operator-required-wallets` появились три необязательных поля с последним зафиксированным отказом по кошельку.
2. Появился `POST /informer/v1/operator-required-wallets/{wallet_id}/refund` — возврат средств, когда обработать кошелёк невозможно. Требует TOTP поверх HMAC.

Оба изменения обратно совместимы, порядок деплоя произвольный.

## Почему это целиком бэкендная работа

Мобильный клиент — generic-рендерер: он превращает `[ACTION:метка]` в кнопку и отправляет **саму метку** обычным текстовым сообщением в чат (`AiBotContent` в `chat_room_screen.dart`). Свободный ввод — тоже обычное сообщение. Поэтому и мастер возврата, и ввод адреса, и ввод TOTP реализуются целиком на бэкенде, как уже сделано для retry. Flutter не трогаем.

## Архитектура

`informer-bot.service.ts` уже 703 строки, а мастер возврата — пятишаговый автомат с двумя развилками. Разносим:

| Файл | Ответственность | Зависимости |
|---|---|---|
| `informer.pending-state.ts` | Типизированное pending-состояние оператора в Redis: load / save / clear. Один ключ, один TTL. | RedisService |
| `informer.refund-flow.ts` | Чистый переход «текущее состояние + ввод → новое состояние + сообщения». Без Redis и HTTP внутри. | типы, форматтеры |
| `informer.refund-errors.ts` | Классификация текста отказа `502` в известные виды. Чистая функция. | — |
| `informer.client.ts` | `+ refundOperatorWallet`, override таймаута на запрос. | — |
| `informer.formatters.ts` | `+` карточки мастера, блок причины, сводка по событиям. | типы |
| `informer-bot.service.ts` | Диспетчер: читает состояние, зовёт flow, ходит в клиент, публикует сообщения. | всё выше |

Отвергнутые варианты:

- **Всё в существующем сервисе.** Сервис уходит за 1000 строк, `parseAction` превращается в кашу, где «6 цифр» значат разное в зависимости от невидимого состояния.
- **Отдельный ключ `informer:pending_refund:{userId}` рядом с существующим `pending_totp`.** Retry не трогается — но у оператора возникают два независимых pending-состояния. Ввод в чате общий на всю беседу, поэтому последовательность «нажал Повторить #1611 → передумал → нажал Вернуть #1620 → прислал код» разрешается недетерминированно: какое состояние первым проверится в коде, туда код и уйдёт. Оператор увидит «Повтор запущен» вместо возврата — по необратимой операции.

Выбран единый ключ: pending всегда ровно один, новая кнопка перетирает предыдущий. Правило «последняя кнопка выигрывает» уже действует в текущем retry, поведение не меняется.

## 1. Pending-состояние и автомат

Один Redis-ключ на оператора: `informer:pending_op:{userId}`, TTL 60 с (как у существующего `pending_totp`), перезаписывается любой новой кнопкой.

```ts
interface WalletCtx {
  network: string;   // withdraw_network
  token: string;     // withdraw_token
  amount: string;    // withdraw_amount
  address: string;   // withdraw_address (адрес вывода, не возврата)
}

type RefundTarget = { address: string } | { toPayer: true };

type PendingOp =
  | { kind: 'retry';  step: 'totp';    walletId: number }
  | { kind: 'refund'; step: 'method';  walletId: number; ctx: WalletCtx }
  | { kind: 'refund'; step: 'address'; walletId: number; ctx: WalletCtx }
  | { kind: 'refund'; step: 'confirm'; walletId: number; ctx: WalletCtx;
      target: RefundTarget }
  | { kind: 'refund'; step: 'totp';    walletId: number; ctx: WalletCtx;
      target: RefundTarget; verifiedAbsent: boolean }
  | { kind: 'refund'; step: 'gate';    walletId: number; ctx: WalletCtx;
      target: RefundTarget; upstreamMessage: string };
```

`WalletCtx` снимается с карточки в момент нажатия кнопки и носится с собой, чтобы карточка подтверждения показывала «50 usdt · BSC → 0xB1c4…», а не голый `#1611`. Список за время мастера мог измениться; перезапрашивать его на каждом шаге дороже и всё равно не даёт гарантий.

Существующий retry мигрирует на этот же ключ как частный случай `kind: 'retry'` с единственным шагом. Ключ `informer:pending_totp:{userId}` перестаёт использоваться.

### Таблица переходов

| Состояние | Ввод | Следующее состояние |
|---|---|---|
| — | `💸 Вернуть #N` | `method` |
| `method` | `📮 Указать адрес` | `address` |
| `method` | `👤 Вернуть плательщику` | `confirm`, `target = {toPayer:true}` |
| `address` | непустой текст | `confirm`, `target = {address}` |
| `confirm` | `✅ Подтвердить возврат` | `totp`, `verifiedAbsent = false` |
| `totp` | 6 цифр | вызов API, состояние очищается |
| `gate` | `✅ Сверил, выплаты не было` | `totp`, `verifiedAbsent = true` |
| любое | `❌ Отмена` | очистка |

Пустая строка или строка из одних пробелов на шаге `address` — не переход: бот повторяет запрос адреса. Платформа обрезает адрес по краям и считает строку из пробелов пустой, так что молчаливая отправка такой строки означала бы неявный `refund_to_payer`.

### Что автомат намеренно не делает

- **Не валидирует адрес по формату сети.** Правил всех восьми сетей мы не знаем, платформа всё равно проверит, а свой валидатор дал бы ложные отказы на легитимных адресах.
- **Не переиспользует `confirm` после ошибки API.** При отказе состояние сбрасывается целиком — кроме двух случаев: «код не принят» (`403`, пересоздаём `totp` на том же кошельке, как уже делает retry) и гейта двойной выплаты (переход в `gate`).

### Гейт по сети для «вернуть плательщику» — отменён 2026-08-26, локального гейта больше нет

> ⚠️ **Пересмотрено повторно 2026-08-26**, тем же днём что и предыдущая версия этого раздела. Тот пересмотр (белый список `{taler}`, fail-closed для всего остального, по требованию Володи «пока давай ограничимся только Taler») оказался построен на неверной посылке и отменяется целиком, а не корректируется.

Ошибка была структурной: `withdraw_network` в ответе `GET /informer/v1/operator-required-wallets` — это сеть, **в которую клиент пытался вывести** (и вывод не прошёл), а не сеть, которой он пополнял кошелёк. Возврат — это возврат пополнения, а не отмена вывода. API **не отдаёт вообще никаких данных о стороне пополнения** — ни сети, ни токена, ни суммы, ни в одном эндпоинте. Живой пример: кошелёк #1646 показывает `withdraw_network: bsc`, но пополнение было в Taler — вернуть нужно TAL, и по `withdraw_network` это никак не отличить от настоящего BSC-пополнения.

Из этого следует, что **гейт по `withdraw_network` в принципе не может работать** — ни как белый список, ни как чёрный, ни fail-open, ни fail-closed. Дело не в том, что список сетей был неверно откалиброван (Taler vs Tron vs шесть остальных), а в том, что сама переменная, на которую смотрел гейт, не относится к возврату. Правки калибровки внутри одного и того же сломанного механизма не чинят это.

Решение: кнопка `👤 Вернуть плательщику` рисуется **всегда, независимо от `withdraw_network`** — рядом с `📮 Указать адрес`, тоже доступной всегда. Решение о том, разрешимо ли «вернуть плательщику» для конкретного кошелька, принимает **платформа** на основе своей истории пополнения, которой у нас нет: карточка подтверждения прямо предупреждает, что это работает надёжно только для пополнений в сети Taler, а при любом другом пополнении платформа отклонит запрос и **ничего не отправит**. Это не деградация относительно прежнего fail-closed — это признание того, что решение не наше и не может быть принято на нашей стороне.

Аргумент про Tron (определение плательщика по истории транзакций там возвращает **подписанта транзакции, а не отправителя токенов**, и им может оказаться hot-кошелёк биржи) остаётся верным сам по себе, но он больше не встроен в код как условие гейта — это факт о платформенной логике, а не о `withdraw_network`, поэтому он живёт в объяснении на карточке подтверждения, а не в ветвлении кода.

Карточки мастера (`formatRefundMethodChoice`, `formatRefundAddressPrompt`, `formatRefundConfirm`) переформулированы так, чтобы `withdraw_*`-поля читались как параметры **несостоявшегося вывода**, а не как предпросмотр возврата — раньше `walletLine()` рендерил `#1646 · 59.7 usdc · bsc`, что оператор мог прочитать как «вернётся 59.7 usdc в bsc», хотя ни сумма, ни сеть возврата в API не приходят вообще.

## 2. Клиент и типы

`InformerClient.signedRequest` принимает необязательный override таймаута. `refundOperatorWallet` зовётся с **45 000 мс** вместо общих 25 000.

Обоснование: возврат — синхронная отправка в сеть, у платформы на неё 30 с. Клиент, отвалившийся по таймауту раньше, не знает, ушли деньги или нет. Док требует не меньше 40 с.

```ts
refundOperatorWallet(
  walletId: number,
  target: { refundAddress: string } | { refundToPayer: true },
  totpCode: string,
  verifiedAbsent = false,
): Promise<OperatorWalletRefundResult>
```

Тело собирается ровно с одним из `refund_address` / `refund_to_payer` — отправить оба означает гарантированный `400`. `withdrawal_verified_absent` кладётся в тело **только когда `true`**: док прямо просит не отправлять его по умолчанию. `wallet_id` дублируется из пути.

Сериализация уже реализована правильно в существующем `signedPost` — один `JSON.stringify`, те же байты идут и в `sha256` для строки подписи, и в тело `fetch`. Пересборка объекта перед отправкой была бы самой частой причиной `401`.

Новые типы:

```ts
interface OperatorWalletRefundResult {
  wallet_id: number;
  status: string;
}
```

`OperatorRequiredItem` дополняется тремя необязательными полями:

```ts
last_error_event?: string;
last_error?: string | Record<string, unknown>;
last_error_at?: string;
```

`last_error` типизируется как объединение, потому что док обещает либо прозу, либо details-payload вида `{"reason":"withdrawal_intent_exists"}`. Форматтер приводит объект к тексту сам, вместо того чтобы падать на нём.

## 3. Классификация отказов

`informer.refund-errors.ts` разбирает `upstreamMessageFrom(body)` по подстроке. Машинных кодов платформа не назначает.

| Подстрока в `message` | Вид | Реакция бота | Кнопка повтора |
|---|---|---|---|
| `refund would be a second payout` | `second_payout` | карточка гейта с чек-листом, переход в `gate` | нет, только «Сверил» |
| `hot wallet holds` … `the refund needs` | `insufficient_hot` | текст + переход к балансам mini-acquiring | да, ничего не отправлено |
| `has no hot wallet payout path` | `no_payout_path` | тупик, обрабатывать вне сервиса | нет |
| `refusing to send blind` | `node_unavailable` | узел недоступен, ничего не отправлено | да |
| `refund operation already exists` | `already_exists` | «возврат уже отправлен, сверяй вручную», красным | **нет** |
| `message === 'refund failed'` | `generic_business` | отказ без деталей | нет |
| ничего из перечисленного | `transport` | пометка «похоже на транспортный сбой» **и текст как есть** | нет |

Последняя строка разрешает противоречие внутри самого дока: он одновременно требует «незнакомый текст показывать оператору как есть, он всегда человекочитаемый» и «`message`, не равный `refund failed` и не совпавший ни с одним известным текстом, считать транспортным сбоем». Делаем и то и другое: классифицируем как транспорт, но текст не прячем — так оператор видит и нашу интерпретацию, и первоисточник.

### Таймаут

`InformerTimeoutError` при возврате обрабатывается отдельно от всех прочих ошибок: «ответ не пришёл за 45 с, транзакция могла уже уйти в сеть, не повторяй вслепую — сверь цепочку». Кнопки повтора нет ни при каких условиях. Автоматического ретрая возврата нет нигде в коде.

Если оператор всё же повторит вручную и получит `refund operation already exists for this wallet` — это читается как «первая попытка прошла», а не как новая ошибка. Формулировка карточки `already_exists` написана именно так.

### Снятие гейта двойной выплаты

Состояние `gate` рендерит карточку, которая перечисляет, что именно надо было проверить (нет исходящей транзакции на адрес вывода на эту сумму в обозревателе соответствующей сети; нет успешного order id в бэкофисе), и явно говорит, что нажатие означает утверждение оператора об отсутствии выплаты и логируется платформой отдельным событием ещё до обращения к бэкенду.

Кнопка одна и сформулирована как утверждение — `✅ Сверил, выплаты не было`, а не `🔄 Повторить`. Флаг `withdrawal_verified_absent` **никогда** не выставляется автоматически, в том числе при повторном проходе мастера.

После нажатия запрашивается **свежий** TOTP: предыдущий код к этому моменту истёк, поскольку сам запрос мог занять до 45 с.

## 4. Список кошельков

Карточка кошелька получает блок причины:

```
🪪 #1611 · BSC / usdt
Адрес: 0xcust
Сумма: 50
Создан: 2026-08-24 17:02:11 UTC
⚠️ withdrawal_to_address_failed
   insufficient balance: have 1, need 5
   2026-08-24 17:03:40 UTC

[🔁 Повторить #1611]
[💸 Вернуть #1611]
```

Шапка получает сводку по `last_error_event`:

```
Причины:
• 3× withdrawal_to_address_failed
• 1× aml_refund_failed
```

Отсутствие полей рендерится **пустотой** — ни «ошибок нет», ни значка проблемы. Поля пропадают в двух случаях: отказов по кошельку не зафиксировано **либо** журнал платформы недоступен. Второй случай нельзя показывать как «с кошельком всё в порядке».

Кнопки `🔁 Повторить` и `💸 Вернуть` рисуются только при наличии `wallet_id` — существующее поведение retry, распространённое на возврат.

Ту же строку причины получает алёрт вотчера о новом кошельке (`formatNewOperatorWalletAlert`): вотчер читает тот же список, поля уже в ответе.

## 5. Защита от параллельных возвратов

Док предупреждает, что защита от двойной отправки на стороне платёжного бэкенда — проверка перед действием, а не гарантия уникальности, и просит не отправлять параллельные возвраты по одному кошельку.

Pending-состояние персональное, а операторов с `informerAccess` несколько. Поэтому на время запроса ставится блокировка по кошельку: `informer:refund_inflight:{walletId}` через `setNxEx` на 120 с, снимается в `finally` после ответа. Если ключ занят — бот отвечает, что по этому кошельку уже идёт возврат, и запрос не отправляется.

TTL 120 с покрывает 45 с таймаута с запасом на случай, если процесс упадёт между запросом и снятием блокировки.

Anti-flood ключуется по `walletId`, как уже сделано для retry.

## 6. Тестирование

TDD, unit-тесты рядом с существующими spec-файлами:

- **`informer.refund-flow.spec.ts`** — таблица переходов целиком: каждый переход из таблицы §1, отмена из каждого состояния, пустой адрес не продвигает состояние, гейт по сети (taler / tron / известная неподдерживаемая / незнакомая — все три последние fail-closed, см. пересмотр 2026-08-26 выше).
- **`informer.refund-errors.spec.ts`** — по кейсу на каждый из семи видов, плюс два незнакомых текста и обрезанное тело.
- **`informer.formatters.spec.ts`** (дополнение) — карточка с причиной и без неё, `last_error` объектом вместо строки, сводка по событиям, отсутствие сводки при полном отсутствии полей.
- **`informer.client.spec.ts`** (дополнение) — тело с ровно одним из двух полей, `withdrawal_verified_absent` не уходит при `false`, таймаут 45 с, подпись от точных байт тела.
- **`informer-bot.service.spec.ts`** (дополнение) — миграция retry на общий ключ не ломает существующие сценарии; блокировка по кошельку отклоняет второй параллельный возврат.

Интеграционной проверки против живого API до заведения TOTP-секрета не будет — см. блокеры.

## 7. Выкатка

Обычный pipeline `DEV → TEST → PROD` из `CLAUDE.md`. Мобильных сборок не требуется. Новых переменных окружения не появляется — ключ и секрет HMAC уже настроены, TOTP-секрет живёт на стороне платформы и привязан к `X-Informer-Key`.

## 8. Внешние блокеры

1. **TOTP-секрет для возврата.** Платформа заводит секрет, привязанный к нашему `X-Informer-Key`. Неизвестно, тот же ли это секрет, что уже работает для retry, или отдельный — спросить Володю (владелец admin-API). Без него возврат отвечает `403 2fa not enrolled for this key`. Код и тесты от этого не зависят.
2. **Платёжный бэкенд не в релизе.** До релиза список не отдаёт поля `last_error*`, а возврат без адреса попадёт в старый обработчик, который адрес по-прежнему требует, и вернёт `400`. Пять текстов `502` предполагают выпущенный бэкенд. Наша обработка обоих случаев корректна заранее и не требует правок после релиза платформы.
